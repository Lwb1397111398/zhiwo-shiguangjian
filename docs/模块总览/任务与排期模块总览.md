# 任务与排期模块总览

## 职责一句话
把"目标 → 计划 → 任务 → 每日打卡"这套东西的定义与"今天该做什么"的计算，收在一处实现。

## 运作流程（数据从哪来 → 怎么处理 → 产出什么 → 影响谁）
1. **进来**：用户在安排页右上角 `+` 建任务（`ScheduleScreen.kt` 的 `TaskEditorSheet`），或由记录页 AI 抽取自动建（`InputViewModel.kt:156-166`，走的是老 `taskType` 字段）。
2. **落库**：一律经过 `TaskWriteBridge`（`data/repository/TaskOccurrenceRepository.kt` 文件内）。它同时写两套：新列（真值，`tasks.kind/repeatRule/…` 15 个字段）和老列（`taskType/isCompleted/dailyCompletionDate`，v13 时是给闹钟与开机恢复读的——F 轮之后闹钟已改读新列，老列只剩导出兼容与回滚保险，v14 删）。反向也写：只填新字段时，桥接会用 `kind + scheduledDate + remindTime` 合成老列的 `taskType` 和带时间的 `dueDate`，否则 `SmartScheduleManager`/`BootReceiver` 读不到时间，用户新建的任务不会响铃。
3. **打卡**：`TaskOccurrenceRepository.setCheck()` 是 `task_occurrences` 的唯一写入口。先按 `(taskId,date)` 查，有则合并字段再 UPDATE，无则 INSERT —— 不用 `REPLACE`（自增主键下 `REPLACE` 根本不幂等，见 `LegacyTaskMapper` 注释与 `AppDatabase` 迁移）。撤销完成写软标记 `pending`，不删行，用户填过的原因要留着。
4. **算今天**：`TaskScheduleEngine.entriesFor(日期, 任务, 当天打卡, 日型, 计划状态表, 目标状态表)` 返回四个段（每日固定/每日留白/临时今天/杂项）+ 已过期 + 漏做 + 已完成，以及完成率的分母分子。规则全部在这个文件里：区间、`everyday/weekdays/custom/interval`、`workday_only/holiday_only`、临时任务"到那天才出现、过了就过期"、留白回填。**adhoc 判后了结**（2026-10-12，设计 §2.1）：只要该任务出现过任意一条 done/not_done 打卡即视为"有了结论"，次日起不再出现（当天仍如实显示✓/✗）；pending（撤销）不算，撤销必能复活。过期判据与 `adhocOverdueOn` 统一：出现日～期限日之间算"待做"，过期限才算过期；过期段同样吃 active 门控（任务暂停/归档、归属计划暂停/目标终结 → 一律不出现）。
5. **日型从哪来**：`HolidayCalendar`（内置法定假日表，**目前为空**，见已知坑）+ `day_overrides` 表（用户手标班/休）→ `dayTypeOf()`。
6. **影响谁**：安排页（`ScheduleScreen`）、记录页统计、AI 评价/日记的任务口径（**尚未接入，仍读老列**）。

## 关键数据结构
- `tasks.kind`：`daily` 每日固定 / `adhoc` 临时一次 / `blank` 每日留白。
- `tasks.repeatRule`：`everyday` / `weekdays` / `custom`+`weekdaysCsv`（ISO 周一=1…周日=7）/ `interval`+`intervalDays`（锚点=开始日，缺则创建日）。
- `tasks.dayPolicy`：`all` / `workday_only` / `holiday_only`。
- `tasks.scheduledDate` vs `dueDate`：前者"哪天开始出现在今天"，后者"最后期限，过了就过期"。
- `task_occurrences.status`：`done` / `not_done`（带 `reasonCode`+`reasonNote`）/ `pending`（撤销）。`note` 装留白回填内容，`actualMinutes` 装实际时长。
- `tasks.status`：`active` / `paused`（编辑器"暂停"进入，总览页"恢复"出来）/ `archived`（老「真正完成」的等价物就是 `archived`；结束在编辑器、恢复在总览页，双向都有门）。完整状态机见 `docs/迭代计划/2026-10-12-任务目标计划生命周期重设计/设计-演进路径与删除语义.md` §2.1。

## 八、任务真删除、计划总览与生命周期总控（2026-10-12 加，同日重构）

**任务删除与恢复的完整出口**（此前任务只能"结束"=归档，没有真删入口；归档后又无处可恢复）：
- 入口在安排页 `TaskEditorSheet`（编辑已有任务时）：「暂停」/「结束任务」/红色文字按钮「删除任务（连打卡记录一起删）」——三种语义分行分色：暂停=暂时停排可随时恢复、归档=保史可恢复、删除=抹史不可恢复。
- 按下删除后先数这条任务的打卡条数（`ScheduleViewModel.occurrenceCount`），确认框如实报数："这会删掉任务本身、它的 N 条打卡记录和提醒，删完找不回来"；任务若挂着来源记录（由记录转来/AI 派生），确认框额外写明"删任务不会删记录，它会回到杂项待办"。数没回来不允许确认。
- 执行一律经 `TaskLifecycle.deleteForever`：先 `SmartScheduleManager.cancelAlarm` 停闹钟与系统日历事件，再 `TaskDao.deleteTaskById`；`task_occurrences` 按外键 CASCADE 跟着删，这是确认框必须报数的缘故。
- **已归档/暂停任务的唯一可触及处是计划总览页**（它们不再出现在安排页，编辑器进不去）：总览页任务行带「恢复」「删除」两个动作，删除走同款确认（`PlansOverviewViewModel` 复用 `TaskLifecycle`）。
- 目标也有物理删除入口了（目标详情页底栏「删除目标」）：`GoalDetailViewModel.deleteGoal` 事务内 plans/taskDao 双摘链（goalId→NULL）后删行——只摘链不连坐，其下计划与任务转自由，总览页"自由块"兜住（`TaskDao.detachTasksFromGoal`、`PlanDao.detachFromGoal` 由此从死代码变为现役）。

**计划总览页**（`PlansOverviewScreen`，路由 `plans`）：
- 给老板核对"该写的都写上去了没有"：整棵 目标→计划→任务 树平铺一页，**所有状态都在**（active/paused/archived/achieved/abandoned 一个不藏），并兼任终态任务的恢复/删除管理台。
- 数据装配：`PlansOverviewViewModel` 合流 `TaskDao.getAllTasks`+`PlanDao.getAllPlans`+`GoalDao.getAllGoals` 三路 Flow → `data/tasks/PlanHierarchy.kt` 的 `buildOverview` 纯函数分组排序（8 条 JVM 单测：排序规则、无主计划、指向已删目标的兜底块）。归属口径与 `GoalDetailViewModel.buildState` 一致：`planId==null && goalId==目标` 算计划外直挂。
- 页面：目标块（状态徽标 + 截止 + 计划数）→ 计划卡（时间窗 + 任务数 + 其下任务逐条列出，"空计划"红字提示）→ 计划外任务小字。顶部有「+ 新建目标」「+ 新建计划」按钮（复用 `goal_edit?goalId=0` / `plan_edit?planId=0&goalId=0` 路由）；点计划卡进 `plan_detail`，点目标行进 `goal_detail`。
- 入口：安排页层级区顶部的「我的计划 ›」常驻一行（不随有无数据消失）。
- 已知取舍：归档任务的完成历史仍在（只是不显示在安排页），所以删除确认里给的"结束任务"替代路径对用户是真选项。

**闹钟与状态机的耦合规则**（设计不变量 §三-4，本轮统一）：停铃只发生在状态迁移（暂停/结束/删除/归属终结）——`TaskLifecycle` 里做；勾选完成/撤销**一律不停铃**（此前记录页、日历页勾完顺手 cancel，daily 重复铃被一次勾选永久停掉）；当天误响由 `ReminderGate.shouldRemind` 触发前挡。删记录/记录转记忆/记录合并一律只摘链、不停存活任务的铃（`RecordListViewModel.deleteRecord`、`RecordOrganizer.applyToMemory/applyRecordMerge` 已收敛）。

## 七、闹钟与提醒（F 轮，2026-09-22 改）

判「今天该不该提醒」也只有一处：`alarm/ReminderGate.shouldRemind`（纯函数，单测直接打）。

- 注册：`SmartScheduleManager.scheduleTask` 按新列决定形态——`kind ∈ {daily, blank}` 挂系统级每日重复闹钟（自带自愈，不依赖「触发后再续排」这条会断的链），`adhoc` 挂一次性；`status != active` 或 `remindTime` 为空的一律不注册，并反过来清掉残留码。
- 开机恢复：`BootReceiver` 不再自己读 `isCompleted/dueDate` 拼一次性闹钟（v13 那套让每日任务重启后只响「今天+明天」两枪），改为复用 `scheduleTask` 同一条路径，`syncCalendar=false`。
- 闹钟码：`alarm/ReminderIds`，一个任务一个码（`1_000_000 + taskId`）。旧公式 `t+10000` 配 `+1` 副码会让任务 t 的第二枪撞上任务 t+1 的主码，`cancelTaskAlarm` 又固定多取消 `alarmId+1`，等于「取消 A 掐掉 B」；现在一次只取消一个码，旧码由 `ReminderIds.legacyIds` 在重新注册时显式清掉。
- 触发时判定：重复闹钟不懂「只在工作日做 / 每周三做 / 今天已勾过」，所以 `AlarmReceiver` 收到 `TASK_REMINDER` 后先 `goAsync()` + IO 查库跑 `ReminderGate`，不该响就静默跳过；判不了则照原样响（宁可多响一次，不能变成再也不响）。临时任务额外收紧：引擎的 `isScheduledOn` 对 `adhoc` 只看区间、不看「哪一天出现」，闸门按 `scheduledDate` 补上，否则定在未来某天的任务会天天响。
