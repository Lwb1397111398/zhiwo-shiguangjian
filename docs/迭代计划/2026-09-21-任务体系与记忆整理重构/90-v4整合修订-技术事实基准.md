## 一、SQLite 事实（本机 3.49 实测矩阵，非记忆）

| 结论 | 证据 | 影响 |
|---|---|---|
| `ALTER TABLE ADD COLUMN` **可以**带 `REFERENCES`，条件是该列默认值为 NULL | 官方 lang_altertable | v13 的 `goalId/planId` 可空无默认 → 合法 |
| `ADD COLUMN` 默认值只能是字面量常量；`NOT NULL` 列必须带非 NULL 默认值 | 同上 | 15 个新列按 §三 的写法 |
| **`foreign_keys=ON` 时 `ALTER TABLE RENAME TO` 会把子表 FK 的目标名一起改写**，`PRAGMA legacy_alter_table=ON` 拦不住（它只挡 view/trigger） | 实测四象限：legacy ON + fk ON → 子表 FK 指向 `tasks_old`，`DROP TABLE tasks_old` 后 `task_occurrences` **0 行** | **v14 不能用 RENAME+DROP 守卫，必须"快照子表 → 重建 → 回填 → 断言"**（§四） |
| `PRAGMA foreign_keys=OFF` 在事务内是 no-op；Room 迁移整体在事务内 | 实测（设完 readback 仍为 1）；Android `SQLiteOpenHelper.onUpgrade` 包事务 | 无法用"关外键"绕过 |
| `PRAGMA defer_foreign_keys=ON` 也救不了（DROP 父表后子行立刻清空） | 实测 | 同上 |
| `DROP TABLE` 在 fk 开启时等价于隐式 `DELETE FROM`，会触发 `ON DELETE` 动作 | 官方 lang_droptable | 同上 |
| `legacy_alter_table` 在 SQLite < 3.25（Android 8.x/9 内置 3.19~3.22）**不存在**，未知 PRAGMA 被静默忽略 | 官方 + minSdk 26 | **任何依赖它的写法在最老设备上都是空气**；只有"快照+重建+前后断言"版本无关 |
| `PRAGMA table_info.dflt_value` 对 TEXT 默认值**带单引号**（`DEFAULT 'adhoc'` → `"'adhoc'"`） | 实测 | 与 §二 的 Room 规则连用 |
| `INTEGER PRIMARY KEY AUTOINCREMENT` 不写 NOT NULL 时 `notnull=0`；Room 生成的建表语句带 `NOT NULL` → `notnull=1` | 实测 | 手写 DDL 必须写 `... AUTOINCREMENT NOT NULL` |

## 二、Room 2.6.1 校验规则（反编译 `androidx.room.util.TableInfo` 字节码，非记忆）

1. `Column.equals` 比较顺序：`primaryKeyPosition` → `name`（大小写敏感）→ **`notNull`（永远比较）** → **`defaultValue`（仅当实体侧 `@ColumnInfo(defaultValue)` 非 null 才比较）** → `affinity`（INTEGER/TEXT/REAL/BLOB）。**列顺序不比**。
2. `TableInfo.equals`：列按 **Map 相等**、索引与外键按 **Set 相等** → 库里多一列/少一个索引/多一个索引都失败。`Index.equals` 比 `unique` + 列清单（含顺序）+ `orders`；名字只在两边都以 `index_` 开头时不比。`ForeignKey.equals` 比 `referencedTable`（大小写敏感）+ `onDelete` + `onUpdate` + 两个列清单。
3. `defaultValueEquals` 只剥外层圆括号，**不去单引号** → 写 `@ColumnInfo(defaultValue = "adhoc")` 会生成 `DEFAULT adhoc`（非法/不等），真机抛 `Migration didn't properly handle: tasks`，且**只有升级用户炸、新装用户不炸**（延迟引爆）。
4. **落地规则**：
   - 15 个新字段 **一律不写 `@ColumnInfo(defaultValue=…)`**（实体侧 null → Room 跳过 DEFAULT 比较，零风险）。表侧 DEFAULT 照写（给 SQLite 用）。
   - 新表 DDL 主键写 `INTEGER PRIMARY KEY AUTOINCREMENT NOT NULL`，非空列显式 `NOT NULL`，FK 明写 `ON UPDATE NO ACTION ON DELETE …`。
   - `TaskEntity.indices` 必须扩到 4 个：`Index("recordId")`、`Index("parentGoalId")`、`Index("goalId")`、`Index("planId")`，与迁移里的 `CREATE INDEX` 名字一一对应。
   - `task_occurrences` 需要 `index_task_occurrences_taskId`（FK 自动索引）+ `index_task_occurrences_taskId_date`（唯一）；**声明了 FK 就必须有对应索引**，否则 Set 不等。
   - `day_overrides` 用 `@Entity(primaryKeys=["date"])`：TEXT 主键产生的 `sqlite_autoindex_*` 的 `origin='pk'`，Room 读 `index_list` 时按 origin 过滤（现网 `settings`/`organize_ops` 已是活证据）。
5. `exportSchema=true` 而没给 `room.schemaLocation` **只是 warning，不会构建失败** → DoD 里"grep exportSchema"证明不了产物存在，必须用文件存在性门禁（§五）。
6. Room **只导出当前 `version` 的 schema** → `12.json` 必须在 bump 到 13 之前生成。**已执行**：本轮先只加 `exportSchema=true` + ksp arg 在 version=12 上构建，拿到 `app/schemas/com.zhiwo.shiguangjian.data.db.AppDatabase/12.json`（实测已生成并回传）。

## 三、v13 迁移的写法（取代 A1 v3 §A1.1 的手写 DDL）

**原则：新表 DDL 照抄 13.json 的 `createSql` 与 `indices[].createSql`，不自己编。** 步骤：
1. 实体 + `version = 13` → 编译 → `13.json`（含 `createSql`/`fields[]`/`indices[]`/`foreignKeys[]`）。
2. `MIGRATION_12_13`：新表 = 13.json 原文（把 `${TABLE_NAME}` 替换成真名）；`tasks` 走 `ALTER TABLE ADD COLUMN`，列定义照 13.json 的 `fields[]`（`TEXT NOT NULL DEFAULT 'adhoc'` 之类），FK 列 `INTEGER REFERENCES \`goals\`(\`id\`) ON UPDATE NO ACTION ON DELETE SET NULL`（不带 DEFAULT）。
3. **幂等**：`ALTER TABLE` 无 `IF NOT EXISTS`，二次执行抛 `duplicate column name` → 每条 ADD COLUMN 前先探测：
   ```kotlin
   private fun SupportSQLiteDatabase.hasColumn(t: String, c: String) =
       query("PRAGMA table_info(`$t`)").use { cur -> val i = cur.getColumnIndexOrThrow("name")
           generateSequence { if (cur.moveToNext()) cur.getString(i) else null }.any { it.equals(c, true) } }
   ```
   建表/建索引已是 `IF NOT EXISTS`；补齐这一层后"重试迁移"才真的可用（用例：语句序列跑两遍不抛）。
4. `Migration12To13(private val context: Context)` —— 迁移内要写备份文件，**必须注入 Context**（`Migration.migrate(db)` 拿不到）。
5. `addMigrations` 地板：去掉 debug 破坏性兜底后，若机器上存在 `user_version < 3` 的库，报错是 `A migration from 2 to 13 was not found` → `ensureDatabaseReady()` 在 `user_version ∉ 3..12` 时抛**含版本号与备份路径**的自有异常，恢复页文案区分"太老 → 只能还原备份"。

## 四、v14 破坏性迁移的唯一安全序列（取代 F v2/v3 §F.1）

前提事实：`task_occurrences.taskId → tasks CASCADE`，而 RENAME 会改写子表 FK 目标、DROP 会级联清子表 —— **所以必须"快照 → 重建两张表 → 回填 → 断言"**（已在 SQLite 3.49 端到端跑通：3 条 occurrence 前后逐字节一致、`foreign_key_check` 空、CASCADE/SET NULL 仍生效、`sqlite_sequence` 不变）：

```sql
-- 0) 基线指纹（不只计数，防"列错位而计数不变"）：cnt / sum(id) / sum(length(content))
-- 1) 快照子表（CREATE TABLE AS SELECT 不带任何约束 → 不受级联影响）
CREATE TABLE `task_occurrences_bak` AS SELECT * FROM `task_occurrences`;
-- 2) 重建 tasks：显式列清单，禁 SELECT *
ALTER TABLE `tasks` RENAME TO `tasks_old`;
CREATE TABLE `tasks` ( <13.json 派生的 v14 DDL，去掉 6 个老列，recordId 为 ON DELETE SET NULL> );
INSERT INTO `tasks`(显式列出保留列，含 id) SELECT 同样的显式列清单 FROM `tasks_old`;
DROP TABLE `tasks_old`;                      -- 此刻子表 FK 指向 tasks_old 且它已无行，无副作用
CREATE INDEX index_tasks_recordId / goalId / planId / parentGoalId? —— 按 v14 实体声明建，顺序必须在 DROP 之后
-- 3) 重建 occurrences（同时解决"被级联删空"与"FK 目标名被改写"两个问题）
DROP TABLE `task_occurrences`;
CREATE TABLE `task_occurrences`( 实体逐字对齐 DDL + 两个索引 );
INSERT INTO `task_occurrences`(id,taskId,date,status,reasonCode,reasonNote,actualMinutes,note,createdAt,updatedAt)
  SELECT 同列清单 FROM `task_occurrences_bak`;
DROP TABLE `task_occurrences_bak`;
-- 4) 断言后提交：occurrence 的 cnt/sum(id)/sum(length(content)) 与基线相等；tasks cnt 相等；
--    PRAGMA foreign_key_check 结果为空。任一不符 → throw（框架事务整体回滚，库停在 v13）
```
- 不使用 `PRAGMA writable_schema`（需 integrity_check 收尾、跨设备风险更高，且同样不改写子表 FK）。
- `legacy_alter_table` 最多当"顺手优化"，**不得作为正确性依据**，且 minSdk 设备上不存在。
- 真机不可覆盖的组合（API 26~28 的 SQLite 3.19~3.24）进实测清单，但上面的序列对两个分支都成立。
- 同批清理：`fallbackToDestructiveMigration` 移除、老 6 列与 `TaskWriteBridge`/`resetDailyTasksForNewDay`/`TaskDisplayRules` 的删除一并做（见 F）。

## 七、引擎补充（在 B v3 之上再加三条）

- **G8 有效下界**：`missedOn/unfilledBlanks/streakOf/progressOf` 的扫描下界 = `max(effectiveStart(task), 迁移日)`，`effectiveStart = startDate.ifBlank { date(createdAt) }`；迁移时 `kind='daily'` 且来自 weekly 的行额外把 `startDate` 写成 `date(dueDate)`。

### 回填谓词必须含"已完成/已放弃的目标"（v3 的致命遗漏）
`completeGoal/abandonGoal` 都会把目标记录的 `category` 改成 `"completed"`，而子任务的 `parentGoalId` 仍指向它 → 只按 `category='goal'` 建 goals 会让**用户过去完成的目标连同归属关系凭空蒸发**（恰恰是最该保留的数据）。谓词改为：
```sql
SELECT id, title, content, createdAt, category FROM records
 WHERE category = 'goal'
    OR id IN (SELECT parentGoalId FROM tasks WHERE parentGoalId IS NOT NULL)
    OR id IN (SELECT recordId    FROM tasks WHERE taskType = 'goal')
```
命中但 `category<>'goal'` 的行：仍建 goal，`status` 按原类别取 `'achieved'`（来自 completed）或 `'abandoned'`（按 `MigrationIssue` 记录来源）。
并且：`goals.recordId` **必须写老记录 id**（双写路径 `completeGoal(goalRecordId)` 拿的是记录 id，没这列就找不到对应 goal 行）；`goalId` 派生式子钉死为
`goalId = goalMap[parentGoalId] ?: if (taskType=="goal") goalMap[recordId] else null`，`parentGoalId` 与 `recordId` 指向两个不同 goal 记录时 **parentGoalId 优先 + issue**（`InputViewModel.kt:160` 就在写 `parentGoalId = id` 与 recordId 同值，这组合在真实数据里必然存在）。

### A1 自检里有一条永真，要换掉
「每个被映射行都有非默认 kind」不成立 —— `taskType='once'` 与所有未知 taskType 的映射结果**就是**默认值 `adhoc`。换成按老列反查：
```sql
SELECT COUNT(*) FROM tasks WHERE
  (taskType='daily' AND kind<>'daily') OR (taskType='weekly' AND kind<>'daily')
  OR (taskType='once' AND kind<>'adhoc')
  OR (taskType NOT IN ('daily','weekly','once','goal') AND kind<>'adhoc')      -- 必须为 0
```

## 九、是否引入 sqlite-jdbc（**需老板拍板**，与既有书面决策冲突）

CLAUDE.md:61 记着一条本项目既有决定：*"不为此引入 sqlite-jdbc —— Room 迁移最终需真实 Android SQLite 环境"*。但评审 A1/B 用**一个通用 SQLite 就把我 v14 的守卫证伪了**，说明 CASCADE 清空、FK 目标改写、索引缺失、DEFAULT 引号、重复列不幂等这些风险**绝大部分可以离线证伪**。加 `testImplementation("org.xerial:sqlite-jdbc:3.45.1.0")` + 约 100 行 JVM 适配器后，可新增三条真验用例：`Migration12To13ReplayTest`（建 v12 库→放样本数据→执行迁移→断言，并再跑一遍验幂等）、`Migration12To13StructureEqualsTest`（按 Room 的读法比对 13.json，等价于把"Room 打开会不会拒"从只能真机降为 JVM 已证）、`Rebuild14GrandchildPreservationTest`（occurrence 一条不少 + 反向断言"直接 DROP 会清零"）。
代价：多一个测试期依赖（不进 APK）；桌面 SQLite 比设备新，个别新特性行为可能有差异，所以**真机首启仍是复核，只是不再是唯一防线**。
我的建议：**采纳**（这是本轮性价比最高的一步，能把"只能等真机"的风险提前到今天暴露）。属于"新增依赖 + 推翻既有书面决定"，所以按规矩请你点头。
