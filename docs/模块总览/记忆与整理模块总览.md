# 记忆与整理模块总览

## 职责一句话
把"关于老板的长期事实"（记忆）存住、改对、不重复；并提供"整理页"这套先看提案再动手的两阶段操作。

## 运作流程

### 一、记忆从哪来
1. **AI 提取**：每天生成评价时（`ui/viewmodel/ReviewViewModel.kt`）让模型从当天记录里抽"关于用户的稳定事实"，写进 `memories` 表；写入前先过一道去重（`filterNewMemories`）。
2. **记录保存后对账**：`ZhiwoApplication.memoryReconciler`（`data/memory/MemoryReconcileService.kt`）拿新说的事与现有记忆比，冲突则把旧记忆标 `under_review` 并进"待确认"队列（存 `settings` 表的 `memoryPendingCorrections`，上限 20 条）。
3. **目标达成/放弃**：`GoalDetailViewModel` 把结论当"用户确认的事实"送进同一套对账。
4. **整理页 / 记忆页的 AI 建议**：见下面第三节，走提案表。

### 二、状态机
`memories.status`：
- `active` 生效，会注入 AI 提示词；
- `superseded` 已被更正取代（`supersededBy` 指向新那条），不再注入，只在「已更正」二级页可见；
- `under_review` 有待确认冲突，暂不注入，等用户在待确认卡片上点"应用/忽略"。

### 三、整理页两阶段（为什么不会"一按就丢数据"）
1. **Plan**：只调 AI + 写 `organize_ops` 表（提案），**不碰业务表**。载荷 `payloadJson` 自包含源 id 与内容 hash。
2. **审核 UI**：逐条勾选/改文本/忽略；忽略会**沿依赖链级联取消**下游（`data/memory/DependencyCascade.kt`，"多父需全父都取消"才级联，带环检测），并提供"撤销忽略"。
3. **Apply**：`data/organizeops/OrganizeOpExecutor.kt` 按固定顺序逐条独立事务执行：
   `EVOLVE_MEMORY → MERGE_MEMORY → SPLIT_MEMORY → DELETE_MEMORY → SAVE_MEMORY → DELETE_SOURCE`。
   每条执行**在事务内重读现场**：目标记忆已不是提案时的状态或内容被改过 → 抛 `OpStaleException` 标 `STALE`，不回滚别的条目。
   删除记录走 `RecordRepository.deleteRecordKeepingTasks`：任务与打卡记录保留，只断掉 `recordId`。

### 四、七种操作类型（`data/organizeops/OpPayloads.kt` 的 `OpType`）
`SAVE_MEMORY` 存新记忆 / `EVOLVE_MEMORY` 改写并取代 / `MERGE_MEMORY` 多条并一条 / `SPLIT_MEMORY` 一条拆多条 / `DELETE_MEMORY` 彻底删除（唯一物理删记忆的动作，二次确认）/ `DELETE_SOURCE` 删来源记录与评价。
**新增类型必须同时改三处**：`OpType.executionOrder()`、`OpValidator.decide()`、`OrganizeOpExecutor` 分支。目前只有 `OpValidatorTest` 逐类型断言，**没有"遍历所有类型"的注册表测试**：漏改一处不会编译报错，只会静默走 `else` —— 这是已知缺口，记在这里。

### 五、判重（"整理完还剩同义记忆"的主因）
`data/memory/MemorySimilarity.kt`：先归一化（去空白、全角转半角、去标点、小写），再判 `EXACT / CONTAINS / SIMILAR / DIFFERENT`。
- 相似度用 **Dice 系数**取"单字符集合"与"bigram"两路的较大值，阈值 0.70。用 Jaccard 会把「我喜欢跑步」与「我喜爱跑步」判成两条不同记忆（0.67 < 0.72），这正是"越整理越多"的成因。
- **数字即事实**：两条记忆的数字串不一致 → 直接判 `DIFFERENT`。否则「我今年25岁」和「我今年26岁」的 Dice 高达 0.83 会被合成一条，把事实吃掉。
- 只有 `EXACT/CONTAINS` 允许自动合并；`SIMILAR` 只提示"疑似重复"，等人确认。

### 六、上限与清理
- 记忆上限 100 条只约束 `active`（`MemoryDao.getMemoryCount` 的 SQL 带 `status = 'active'`）。
- `superseded` 由启动维护（`ZhiwoApplication.pruneSupersededMemories` + `data/memory/MemoryRetention.kt`）保留最近 30 条，超出的**先归档成 JSON**（`getExternalFilesDir("migration_backup")/superseded_archive_<ts>.json`）再删，并在日志写明条数。
- 排序用 `createdAt`（真正写库的时间），"来自哪天"用 `occurredAt` 显示——两者混用过会导致刚整理的记忆因 createdAt 很旧而被上限挤掉。

## 对外接口 / 被谁调用
- `MemoryRepository.getActiveMemories()` → 评价、日记、画像更新、整理提案等 6 处提示词注入点。
- `memoryReconciler.reconcileAndApply(...)` → 保存记录后、每日评价、目标达成/放弃。
- `OrganizeOpExecutor.apply(op)` → 整理页"应用"与记忆页"AI 建议"（后者现在也生成提案，不再自己硬删）。

## 已知坑与约束
1. **`organize_ops` 的历史行**（本轮之前生成的提案）载荷里没有 `memoryIds`/`contentHashes`，新执行器只能把它们判 `STALE` 让用户重新生成——不要指望旧提案还能执行。
2. **AI 契约决定去重上限**：`classify/smartClean` 现在回传 `{text, items:[序号]}`，序号按传入列表 1 基编号。模型若不按格式给序号，该条建议被丢弃并计数（**不再退化成"删全部"**——那是上一版"一键整理反而删光"的成因）。
3. `enforceMemoryLimit` 在事务外调用，且整理一次跑多条时会多次触发；淘汰只淘汰 `superseded`（在 `MemoryRepository` 里强制），不会误删 active。
4. 「已更正」二级页的"彻底删除"是唯一不可恢复的入口，必须走 `DELETE_MEMORY` 提案或该页二次确认。
5. 待确认队列被上限挤掉时，对应记忆必须打回 `active`（`MemoryReconcileService` 里已处理）；否则会出现"既不注入也看不见"的幽灵记忆。
6. 未验证项（本机无模拟器）：真机升级后 `occurredAt` 回填、记忆条数与整理闭环 → 见「用户实测清单」第 16-18 条。
