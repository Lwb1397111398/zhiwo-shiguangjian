## F.1 v14 破坏性迁移（删老列 + recordId 改 SET NULL）

前置：确认 §8.1 门禁在 v13 下已全绿若干轮，且老板已装 APK-1 无异常（**这是唯一能证明 v13 结构被真机接受的证据，没拿到就不发 v14**）。

```sql
-- MIGRATION_13_14：重建 tasks（SQLite 不支持可靠地 DROP COLUMN，Android API 26 的 3.19 更不支持）
PRAGMA legacy_alter_table = ON;                      -- 关键：让 RENAME 不改写其它表 FK 子句里的目标名
-- 0) 记录守卫基线：oc0 = SELECT COUNT(*) FROM task_occurrences; tk0 = SELECT COUNT(*) FROM tasks;
1) ALTER TABLE `tasks` RENAME TO `tasks_old`;         -- 用 RENAME 而非 DROP，避免 CASCADE 当场清空打卡史
2) CREATE TABLE `tasks` ( <22 列，无老列；
     recordId FK → records ON DELETE SET NULL;        -- v1 的 CASCADE 是"整理删记录连带抹掉每日任务"的元凶
     goalId  FK → goals   ON DELETE SET NULL;
     planId  FK → plans   ON DELETE SET NULL );
3) INSERT INTO `tasks` SELECT <新列清单> FROM `tasks_old`;
4) DROP TABLE `tasks_old`;                            -- 此刻没有任何子表引用它（因 legacy_alter_table）
5) CREATE INDEX index_tasks_recordId / goalId / planId;
PRAGMA legacy_alter_table = OFF;
-- 6) 守卫：oc1 == oc0 且 tk1 == tk0，否则 throw（迁移整体回滚，rebuild 路径保数据）
```
坑说明（必须写进代码注释）：`Room` 迁移在事务内执行，而 `PRAGMA foreign_keys=OFF` 在事务内是 no-op；若直接 `DROP TABLE tasks`，`task_occurrences.taskId` 的 `ON DELETE CASCADE` 会被 SQLite 隐式触发，**把所有打卡记录清空**。因此顺序固定为「RENAME 改名 → 建同名新表 → 拷数据 → 删旧表」，并用 `legacy_alter_table` 阻止 RENAME 把子表 FK 目标改成 `tasks_old`。前后计数守卫是最后防线。
其它：v14 前再做一次三件套文件级备份（`pre_v14_<ts>`）；`exportSchema` 产出 `14.json`；`SchemaVsMigrationConsistencyTest` 扩到 v14。
