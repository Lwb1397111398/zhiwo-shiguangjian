## 0. 本轮新核出的硬事实（我自己跑出来的，不是转述）

- **E1 `INSERT` 必须显式带 `id`**。不带 id 重建父表 → 行号从 1 重排，而快照里 occurrence 的 `taskId` 是 7/9/12 → **回填后每条打卡都挂到别的任务上**（不是"可能"，是必然）。
- **E2 `DROP TABLE` 父表会把子表级联清空**：本机 SQLite 3.49 复现，`task_occurrences` 由 3 行变 **0 行**。所以 v5 里"此刻 tasks_old 已无行、级联无副作用"的说法**是错的**：安全**完全依赖** CTAS 快照 + 第 6 步回填，而不是依赖顺序侥幸。
- **E3 `ALTER TABLE … RENAME` 会改写子表外键目标**：复现中改名后再往 `task_occurrences` 插行直接报 `no such table: main.tasks_gone`。⇒ 第 6 步必须**重建** `task_occurrences`（DDL 里 FK 写死指向 `tasks`），不能"沿用旧表"。
- **E4 `InputViewModel` 造的 AI 任务 `goalId` 恒为 NULL**：`goalIdOf = { null }`、构造 `TaskEntity` 时只给 `parentGoalId`（`ui/viewmodel/InputViewModel.kt:160-188`）⇒ **v14 若只删列不回填 `goalId`，用户自己建的"属于某目标的任务"会集体失联**（掉到没有目标的状态）。
- **E5 `CalendarContract.Calendars` 没有 `OWNER_NAME` 列**（本机 SDK 源码 `provider/CalendarContract.java`：只有 `ACCOUNT_NAME:359`、`ACCOUNT_TYPE:367`、`CALENDAR_DISPLAY_NAME:442`、`OWNER_ACCOUNT:501`），且 `ACCOUNT_TYPE_LOCAL = "LOCAL"`（`:230`）。⇒ v5 F-g 的白名单四个取值**全部落空 = 静默不生效**，`COALESCE(…, OWNER_NAME)` 是会抛 SQL 错误的写法。
- **E6 `scheduleRepeatingTaskAlarm` 仍在被调用**（`alarm/SmartScheduleManager.kt:86,104` → `alarm/AlarmScheduler.kt:217-239`）。同一 requestCode 上"后注册的单发会替换重复闹钟"，所以 F-a 若不改这两个分支，**老板抱怨的"只响一天"会以新形式回来**。
- **E7 `tools/verify.sh`**：`:53` 把镜像 schema 拷回真目录、`:55` 再对二者 diff ⇒ 结构上永不 FAIL（假门，确认）；`:84-87` **已经在输出类级用例数**，`:62-70` 没有任何用例数比较 ⇒ 对账要接在这段后面，别另造一套。

## 1. R4 升级失败门（重写，解决 M3）

v5 的写法有个致命时序错：迁移在 `ZhiwoApplication` 的 IO 协程里异步跑，而 `MainActivity.kt:58-64` 首帧就 `syncFixedAlarms` 并 `app.database.settingDao()` 取库 ⇒ **第一次真失败时门还没立起来，UI 已经崩在前面**。改为：

1. `AppDatabase` 仍是 `by lazy` 单例 ⇒ **谁先碰谁付迁移的代价**。本轮把它固定成"只有门协程先碰"：`ZhiwoApplication` 在 `IO` 作用域里首次访问 `database`（同步完成 Room 建库+迁移，不再预热后又异步 catch），结果写进 `DbGate`。门立起来之前，`MainActivity` 不组 `NavHost`，所以 13 个含 `app.database` 取用点的 ViewModel（构造期即取库的代表：`CalendarViewModel:28-37`、`DiaryViewModel:38-45`、`InputViewModel:37-44`、`MemoryViewModel:29`、`GoalDetailViewModel:111`）不会提前触发；**F-d 第一步就是把这 13 个文件逐个标注"构造期取库 / 协程内取库"**，构造期取库又不受门控的先改成 `by lazy`。
   ⚠️ 残留口子：`AlarmReceiver`/`BootReceiver` 走 `AppDatabase.getInstance(context)`，门之外也能开库——它们本来就在广播线程，迁移在那里发生不算 ANR，但**必须把 `DbGate` 标成"已由外部打开"**，否则冷启动只收闹钟不进 App 时门永远立不起来。这条写进用例 MF-d6。
2. `MainActivity` 用 `sealed interface DbState { Upgrading; Ok; Failed(info) }` + `StateFlow`，**首帧只渲染 Splash/失败页**；`MainActivity.kt:58-64` 现有的 `syncFixedAlarms` 与 `app.database.settingDao()` 两处首帧取库**必须挪到 `Ok` 之后**（这是 v5 漏掉的具体改动点）。
3. 失败信息落 `db_state.migrate_failed`（from/to、异常类名+message、时间、**累计失败次数**）。`次数 ≥ 2` 时失败页额外显示"这台机器的数据可能搬不过去，可清空重建或先导出"——**不自动清库**（R2/R4 不变）。
4. **成功开库必须清标记**：`DbState.Ok` 达成后 `remove("migrate_failed")`；否则清空重建之后会永远卡在失败页。这是 v5 完全没写的一步。
5. `rebuild_confirmed` 的崩溃窗口：写入该标记 → 冷启动时**先检查它**，为真则幂等续做 rebuild（`rebuild()` 本身先备份后删文件，重跑安全），做完清标记。
6. `CLAUDE.md:60` 那句"迁移失败 → 备份并重建"的旧约定必须与本轮**同批**改掉（S5），否则文档与代码互相打脸。

## 2. F-a 闹钟地基（重写，解决 M5/M6/E6/E7）

- 新码表：`requestCode = 1_000_000 + taskId*16 + slot`（slot 0=当日、1=续排、2..15 保留），`notificationId = 5_000_000 + taskId`。不相交的算法说清楚：旧码是 `t'+10000`/`t'+10001`（`SmartScheduleManager.kt:20-23`），新码最小 1,000,000 ⇒ 只要 `t' ≤ 989,999` 两个集合就不可能重叠（真实任务数差好几个量级）；Int 上限这边 `taskId ≤ 133,141,568` 时 `1_000_000 + taskId*16 + 15` 仍不溢出，故加 `require(taskId in 0..130_000_000)` 兜住。MF-a3 写成"对 `t ∈ 0..100000` 断言新旧码集合无交集，且均不与 `AlarmData.kt` 的 1001~1004 及 `NotificationHelper` 固定通知 id 重叠"。
- **sweep 必须遍历全表**（含 `archived`/已完成/暂停），因为旧码是在这些任务还活跃时注册的；只扫未完成任务会留下一批"幽灵闹钟"。跑法：`db_state.alarm_id_v2` 未置 2 → cancel 每个任务的 `t+10000`、`t+10001` 两个 requestCode + `NotificationManager.cancel(同两个 id)` → 全部成功才置 2；cancel 幂等故崩溃可重跑。
- **删掉重复闹钟这条路**：`scheduleRepeatingTaskAlarm` 与 `AlarmScheduler.kt:217-239` 的 `setInexactRepeating` 分支、`SmartScheduleManager.kt:86,104` 的调用**一并移除**（E6），任务提醒统一"单发 + 触发后续排"（R5）。四个注册点（saveTask / 勾选 / 开机 / onStart 校对）收敛到唯一入口 `TaskReminderPlanner.plan(db, task, today)`，返回"注册/取消/无动作"，别处不许自己算。
- `onStart` 增量校对要有节流：`TaskReminderPlanner` 只在 `nextScheduledDate` 与已注册日不同时才动 `AlarmManager`；地平线沿用 400 天，但**每次启动最多校对 500 个任务**并按 `remindTime` 排序，避免开机首帧卡顿。

## 4. F-f 迁移序列（v5 §F-f 作废，以本节为准；解决 M1/E1/E2/E3 + S1/S2）

```
0) 基线指纹：tasks / task_occurrences 的 cnt、sum(id)、sum(length(content))、三态计数；
   并记 foreign_key_check 的**基线行数**（不是要求为 0，见 S2）
1) CREATE TABLE task_occurrences_bak AS SELECT * FROM task_occurrences        -- CTAS 无约束，免疫级联
2) ALTER TABLE tasks RENAME TO tasks_old                                      -- 子表 FK 目标被改写（E3），故此后不许再往旧 occurrences 写
3) CREATE TABLE tasks ( 20 列 v14 DDL，recordId 外键 ON DELETE SET NULL )
   INSERT INTO tasks(id, …保留列…, goalId, endDate)                          -- 必须显式带 id（E1）
     SELECT id, …, COALESCE(goalId,(SELECT g.id FROM goals g WHERE g.recordId=tasks_old.parentGoalId)),
            CASE WHEN kind='adhoc' AND endDate='' THEN substr(dueDate,1,10) ELSE endDate END
       FROM tasks_old
4) DROP TABLE tasks_old                        -- 此刻级联真的会清子表（E2），靠第 1/6 步保数据
5) CREATE INDEX index_tasks_recordId / _goalId / _planId ON tasks             -- 只 3 个；必须在改名之后；DDL 从 14.json 抄但要**去掉 ${TABLE_NAME} 占位符并逐字核对表名**，
                                                                              --   IF NOT EXISTS 保留无害，**表名替换错=静默 0 索引**（Room 事后校验才发现 → 断言里先自查）
   第 5 步末：`SELECT count(*) FROM sqlite_master WHERE type='index' AND name LIKE 'index_tasks_%'` 必须 == 3，不等即 throw
6) DROP TABLE task_occurrences                                                 -- 旧表 FK 目标已被改写，不修不行（E3）
```

## 10. v6 第四轮评审 V6-N1…N8 的补丁（本节优先级最高，与前文冲突以本节为准）

- **N1 E3 不是普适事实**：`ALTER TABLE RENAME` 改写子表 FK 目标只在 **SQLite ≥ 3.25**；minSdk 26/27 的 3.19~3.24 上**不改写**，`DROP tasks_old` 也就**不级联**。⇒ §0 的 E3 降级为"≥3.25 行为"；迁移第 2 步前先取 `PRAGMA foreign_key_list(task_occurrences)` 的当前目标名，**两个分支都按"快照→重建→回填→断言"走**（这套序列对两边都成立），并要求 MF-f9 断言"无论 FK 目标名是什么，occurrences 回填后行数与内容等于基线"。
- **N2 第 6 步会被脏外键整事务打死**：`INSERT…SELECT FROM task_occurrences_bak` 只要有一行 `taskId` 在新 tasks 里不存在就抛 `FOREIGN KEY constraint failed` → 回滚 → 用户 100% 卡失败页，S2 的"比基线"根本没机会生效。⇒ 第 6 步前先 `DELETE FROM task_occurrences_bak WHERE taskId NOT IN (SELECT id FROM tasks)` 并把条数存进局部变量 `dropped`；**第 7 步的所有 occurrence 判据一律改成 `== 基线 − dropped`**（cnt、sum(id)、sum(length(content))、三态计数全套，否则放宽等于没放宽），`foreign_key_check 行数 <= 基线行数`；`PRAGMA foreign_key_check` **只在第 0 步与第 7 步读**（实测：父表被 DROP 之后它不报错，而是把全部子行报成违规，中间态读它会自欺）。夹具必须包含一条**脏 occurrence**（taskId 指向不存在的任务），并断言它被计入 `dropped` 而不是让迁移红。
  说明白残留风险：FK 是 CASCADE，理论上不该有脏行；脏行只可能来自历史 bug 或人工改库。本条不是"怀疑有脏数据"，是"万一有就不许把用户关在门外"。
- **N3 取消侧必须与注册侧同批改**：注册入口除 saveTask/勾选/开机/onStart 校对之外**还有 AI 建任务**（`ui/viewmodel/InputViewModel.kt:213`）；取消点现有 9 处（`RecordOrganizer:54,108`、`CalendarViewModel:121`、`GoalDetailViewModel:259`、`RecordListViewModel:158,214,237,319`、`ScheduleViewModel:222,254`）仍按旧码算 → 新码闹钟永远取消不掉（幽灵提醒）。⇒ 全部收敛到 `TaskReminderPlanner.plan(task)` / `.cancel(task)` 两个入口，且 `AlarmScheduler.cancelTaskAlarm:254-271` 里那句"顺手多取消 `alarmId+1`"必须删（新码表下它会误杀同任务的下一个 slot）。
- **N4 `goalId` 回填打不到 AI 那批**：回填 SQL 依赖 `goals.recordId`，而 goals 行只由 v13 回填和 `applyTodosToGoal` 产生；AI 当场新建的目标记录没有 goals 行 → 这类 `parentGoalId` 行**救不回来**。⇒ ①如实写"回填仅覆盖已成目标的行"；②F-c 顺手修 `InputViewModel`：新建目标时同事务插 `goals` 行并直接写 `goalId`（不再依赖 `goalIdOf={null}`）；③`MigrationIssue` **不建新表**（新增实体本身就是 schema 变更），改为 `Log.w` + 迁移结束把计数写进实现日志，由我在真机升级后读 logcat 汇总。
- **N5 升级门要挡住的是"整个进程"，不只有 NavHost**：`MainActivity.kt:117` 的 `memoryReconciler` 会在构造期经 `ZhiwoApplication.kt:26-32` 拿 `database.memoryDao()`；`AlarmReceiver.onReceive` 跑在**主线程**且现在根本不碰库。⇒ ①门未 `Ok` 之前 `MainActivity` 不 `setContentView` 之外的任何依赖注入路径；②`AlarmReceiver` **不取库**：注册时把"该不该响"的判定日期写进 Intent，触发时只做字符串比较（R5 的引擎校验放在注册侧，不在广播侧现取现算）；③失败计数以 `(from,to,进程代次)` 去重且只由门写、`commit()` 同步落盘；`AlarmScheduler.kt:27-31` 那种吞 Throwable 的旁路不得消耗迁移机会。
- **N6 `verify.sh` 的 drift 还有盲区**：`:28` 把 `app/schemas` 排除在镜像同步之外、`:39` 又是"真目录→镜像"，所以**构建前就被手改/删掉的 schema** 它看不见。⇒ 基线改成从版本库取：`git show HEAD:app/schemas/<...>/14.json` 的 sha256 清单；用例数基线固定读 `docs/quality/GATE-*.txt` 里最新一份。
- **N7 MF-c5 的 grep 判据不可满足**：`TaskInfo.dueDate`（`data/ai/AiModels.kt:15`）是活的 AI DTO，F-f 之后照样合法。⇒ 判据改为"仅 `TaskEntity` 接收者上的 `.dueDate` 必须为 0"，DTO 侧三处进白名单。
- **N8 sweep 集合与校对集合必须分开定义**：sweep（清旧码）遍历**全表含已完成/归档**；`plan` 的注册前置是 `status=="active" && remindTime 非空 && !isEffectivelyDone(今天)`（复用 `TaskScheduleEngine.kt:164`），每次启动最多校对 500 个、按 `remindTime` 排序取**未完成**集合。两条写成不同函数，禁止实现者复用同一个查询。
- S1 订正：第 5 步索引必须在 `DROP TABLE tasks_old` **之后**建，真正的原因是**旧索引名还挂在 tasks_old 上**，`CREATE INDEX IF NOT EXISTS` 会静默跳过 → 新表 0 索引而 `LIKE 'index_tasks_%'` 数到 4。S2：所有 PRAGMA 读取走 `db.query()`（`AppDatabase.kt:56,233` 的既有写法），`execSQL` 读不到返回值。S3：不相交条件是 `t' <= 989,998`，Int 上界 `134,217,039`。S4：`AlarmScheduler.cancelAllAlarms:273-291` 现零调用，并入 F-e 第 1 刀。S5：导出 JSON 少 7 字段登记为"备份格式变更"。S6：F-g 在老板手机 dump 出真实 `ACCOUNT_TYPE` 之前**不承诺支持任何机型**，批次顺序里标为 BLOCKED-on-真机。S7：sweep 应按"已注册 requestCode 区间"清（`10000..maxTaskId+10001`），按现存任务驱动会漏掉**已被级联删除的任务**留下的旧码。
