## 1. 事实基准（两条调研，逐条标核对状态）

**已核对（grep / 读文件 / Room schema 实证）**

- F1 老列**不是 6 个而是 9 个**：`tasks` 表 v13 实际 27 列，老列为
  `recordId, parentGoalId, dueDate, taskType, isCompleted, completedAt, dailyCompletionDate, isPermanentlyCompleted, calendarEventId`。
  **`repeatType` / `repeatInterval` 全库不存在**（含 `app/schemas/…/13.json`），先前记录写错了，以本条为准。
- F2 `calendarEventId` 是活的（闹钟/日历取消链路 7 处引用）→ **不删**；`recordId` 是"任务↔来源记录"的活关联（`detachTasksFromRecord` 靠它摘链）→ **不删，只改外键动作**。
  ⇒ v14 真正要删的是 **7 列**：`taskType, dueDate, isCompleted, completedAt, dailyCompletionDate, isPermanentlyCompleted, parentGoalId`。
- F3 `parentGoalId` 上有 `Index` 且带 `REFERENCES goals`，`recordId` 同理 → `ALTER TABLE DROP COLUMN` 对"被索引/被外键引用"的列不可用 → **必须整表重建**（快照→建 14 版新表→回填→删旧表→改名→重建索引）。此模式 v13 已实测：`legacy_alter_table` **挡不住 RENAME 改写子表 FK 目标**，所以 tasks 若被别的表引用需"快照子表→重建→回填→前后指纹断言"。经查 `13.json`：无表引用 `tasks(id)`，故本轮只需重建 `tasks` 自身。
- F4 `TaskScheduleEngine.nextScheduledDate(task, from, horizonDays=400, dayTypeOfDate={ null })`：全库**零调用**；默认 resolver 会让 `dayPolicy=workday_only/holiday_only` 的任务永不排期 → 接线时**必须显式传 resolver**，否则是静默失响。
- F5 `BootReceiver:38-72` 只读 `isCompleted / dueDate / taskType / id / content`：`dueDate` 空即跳过（每日/留白任务的老 dueDate 可能为空 → 重启后不响）、过期超 1 小时判死、不看 `status`（暂停/归档靠 `isCompleted` 意外挡住，删列后这层"意外保护"消失）、daily 只补"今天+明天"两枪。
- F6 `SmartScheduleManager.scheduleTask(...)` 签名吃 `taskType/dueDate` 字符串，靠 `taskType` 分支决定"重复闹钟 vs 一次性精确闹钟"。
- F7 `CalendarHelper`（全库唯一 CalendarContract 使用点）`getPrimaryCalendarId` 只投影 `_ID, IS_PRIMARY`，**没有按名字匹配日历的能力**；`addEvent` 之后固定插一条 15 分钟 `METHOD_ALERT` 提醒 → 与自研闹钟**双响**（既有缺陷，本轮如实记账，是否修见 §6 Q3）。日历权限只在 `SettingsScreen` 手动申请，`CalendarHelper` 内部不检查权限，未授权时 insert/query 抛异常被 catch 成 null/空。
- F8 `HolidayCalendar` 只有 2026 数据，`hasDataFor(year)`/`coveredYears()` 已具备；2027-01-01 起 `dayTypeOf` 返回 null，三页走 `dayTypeOrWeekend` 按周末猜并显示提示。
- F9 `db_state.rebuilt_at` 唯一写入点 `ZhiwoApplication.kt:73-74`，**全库零读取**；真正的重启靠紧随的 `killProcess+exitProcess(10)`。迁移失败链路：`ZhiwoApplication:60` 预热 → catch → `AppDatabase.rebuild`（checkpoint→备份 `pre_rebuild_<ts>` 到 `getExternalFilesDir("migration_backup")`，null 时退 `filesDir`→删活库→重建→写标记→杀进程）。当前**没有** `fallbackToDestructiveMigration`，缺迁移必抛。
- F10 死代码实底：`RecordListScreen.kt:206-293` 的旧 `ScheduleTab` **不是注释掉的**，是失去调用方的真函数，删它会连锁失去 `SectionHeader/EmptyHint/ScheduleRecordItem/GoalRecordItem/CompletedRecordItem`（`:516-~750`）与 `RecordListViewModel` 的 6 个成员；`RecordRepository.deleteRecord:49-59`、`TaskRepository` 四个转壳（`getTasksByType/insertTasks/deleteTask/deleteTasksByParentGoalId`）、`TaskWriteBridge.unarchive:91-93` 零调用；`TaskDisplayRules.isTaskEffectivelyCompleted` **是活的**（RecordCard/TaskItem/RecordListViewModel 在用），不能整删，只删 `getTaskDisplayDate/nextWeeklyDate/parseDateOnly` 这条死链。

## 2. 红线（老板 2026-09-22 改口径后新立，优先级最高）

- **R1（本轮唯一一次）**：v13→v14 升级若真出事，允许现在手机上的数据丢掉，不救。
- **R2（永久）**：从 v14 起，任何迁移都必须**增量 + 保数据**。禁止 `fallbackToDestructiveMigration`（含 debug 变体），禁止在迁移里 `DROP TABLE` 后不回填。
- **R3**：v14 迁移自身必须**自证清白**——回填前后各算一次"内容指纹"（`tasks` 行数、每行 `(id, kind, startDate, endDate, status)` 的聚合摘要、`occurrences` 行数、`done/not_done/pending` 三态计数），不一致就 `throw`，让迁移**失败并回滚**，而不是留下半迁移的库。
- **R4**：`rebuild()` 这条兜底路径存在的前提是"已经坏了"，不是"迁移没写"。它触发时必须把发生过什么落成用户可读的提示（§3-2），不再只写一个没人读的标记。

## 3. 四个交付项的设计

### 3-1 开机提醒接引擎（#1）

- 改法：`BootReceiver` 不再读 `isCompleted/dueDate/taskType`。改为：取 `status=="active"` 且 `remindTime` 非空的任务 → `TaskOccurrenceRepository` 拿 occurrences → 调 `nextScheduledDate(task, today, resolver=引擎 dayTypeOrWeekend(带 HolidayCalendar + day_overrides))` → 命中且当天未 `done` 才注册。
- 提醒形态由 `kind/repeatRule` 决定：`daily`/`blank`/`weekly`(custom) → `setInexactRepeating`；`adhoc` → `setExactAndAllowWhileIdle`（无精确权限时按现有降级路径）。
- `SmartScheduleManager.scheduleTask` 签名从 `(taskType, dueDate, …)` 改成吃 `TaskEntity` + 解析后的触发时刻；`ScheduleViewModel.saveTask` / `InputViewModel` 的调用点同步。
- 会红的用例（JVM 纯函数，新增 `NextAlarmResolverTest`）：
  - MF16 暂停/归档任务重启后**不**注册闹钟；
  - MF17 `workday_only` 任务在周六重启 → 下次触发是下周一（不是"永不"、也不是"明天"）；
  - MF18 留白任务（`old dueDate` 为空）重启后仍注册（今天该做时）；
  - MF19 当天已完成的任务重启后不注册；
  - MF20 无 `remindTime` 的任务不注册（不凭空造提醒）。
- 影响面回归：固定 4 个闹钟（`syncFixedAlarms`）不受影响；`AlarmScheduler` 的 requestCode 公式不变（`taskIdToAlarmId`）。

### 3-2 迁移失败对用户可见（#2）

- 改法（最小闭环）：`rebuild()` 成功后用**进程内静态标记 + DataStore `commit()`** 记 `rebuilt_at` 与备份目录名；下次冷启动 `SettingsViewModel` 读一次，设置页顶部出**一条横幅**：「升级时数据库没能搬完，已重建空库；备份文件在 `<目录>`，可联系导出前先用它」+「知道了」按钮（点了清除标记）。
- 会红的用例：MF21 标记写入后能被读到；MF22 点"知道了"后不再显示；MF23 正常启动（没出事）**绝不显示**该横幅。
- 不做：不做"从备份一键恢复"（要读外部存储、要合库，本轮不吞这个复杂度；横幅只告诉你备份在哪）。

### 3-3 v14 破坏性迁移与死代码清理（#3）

### 3-4 节假日接系统日历（#4，如实标注）

- 新增 `DeviceHolidayCalendarSource`：查 `Calendars` 表 `CALENDAR_DISPLAY_NAME` 匹配 `节假日|假期|中国节日|Holiday`，命中日历的**全天事件日期**=休息日；事件标题含 `班|上班|调休|补班` 的=工作日。结果按年缓存。
- 优先级：`day_overrides`（你手动标的）> 内置 `HolidayCalendar`（2026 已核对公告）> 设备日历 > 按周末猜并显示"在猜"提示。
- 未授权 / 无匹配日历 / 查询抛异常 → 一律**静默退到下一级**，并在现有 `holidayWarning` 文案里如实说明"没找到节假日日历，按周末判定"。
- 会红的用例：MF27 手动标记压过设备日历；MF28 设备日历缺失时行为与今天完全一致（回归）；MF29 无权限时不崩不弹（`checkSelfPermission` 前置）。
- 说明白：这不等于"2027 一定准"。手机上有节假日日历才准；没有仍按周末猜。**2027 公告一出我就录**（这条保留为长期项）。
