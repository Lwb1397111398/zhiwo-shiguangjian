## A1.0 v1 为什么作废

v1 的 A 步在迁移里删掉 6 个老列 → 17 个文件、约 20 个判定点**同时编译失败**（评审 B 实测清单），与"每步完成后跑测试"直接矛盾。v2 改成：
**v13 只加不减 + 双写**（老列与老 UI 全程活着，任何一步都可编译、可运行、可回退）；删列推迟到 F 的 v14。

## A1.1 范围（做完必须 `BUILD SUCCESSFUL` + 老功能全部照旧）

1. 新表 4 张：`goals`、`plans`、`task_occurrences`、`day_overrides`；`memories` 加 `occurredAt`。
2. `tasks` 加 15 个新列（§A1.3），**老列一个不删**。
3. `TaskEntity` 同步加这 15 个字段（保持"实体列集合 == 表列集合"，见 §A1.6 的 Room 校验风险）。
4. 存量回填：迁移内用纯函数 `LegacyTaskMapper` 把老数据算成新列值 + 生成 goals 行 + 生成历史 occurrence。
5. 双写：现有 4 条写路径同时写老列与新列（§A1.4）。
6. 备份与失败防线：文件级三件套备份 + JSON 备份回读自检 + 同步化 `ensureDatabaseReady()` + 失败横幅（§A1.5）。
7. `exportSchema=true` + schemas 入库 + 结构对账测试（§A1.6）。

- `ADD COLUMN` 的默认值必须是**字面量常量**（SQLite 限制），所以全部用 `''`/`0`/`1`/字符串常量，不用表达式。
- 新增外键列直接带 `REFERENCES`（列级约束），不依赖表级约束，避免二次重建。
- 顺序纪律：`goals`/`plans` 必须先于 `tasks` 加 FK 列；`task_occurrences` 引用已存在的 `tasks`，随时可建。

## A1.3 回填（迁移内，Kotlin + Cursor，映射用纯函数）

```
1) goals ← 所有 records WHERE category='goal'（不只被 parentGoalId 引用的）→ 建 goal 行，
   内存维护 map<oldRecordId, newGoalId>；title 为空时用 content 兜底，仍空则用「未命名目标」
2) 老 tasks 全表 → List<LegacyTaskRow> → LegacyTaskMapper.mapAll(rows, goalIdOf, today)
   → List<MappedTask{taskId, columnUpdates:Map<String,Any?>, occurrences:List<MappedOccurrence>}>
3) 逐行 UPDATE tasks SET <新列>=? WHERE id=?    （参数绑定，禁止字符串拼接 SQL）
4) INSERT INTO task_occurrences(...) 回填历史打卡
5) 自检：tasks 行数不变；每个被映射行都有非默认 kind；occurrence 条数 == mapper 预期条数；
   任一不符 → throw IllegalStateException（交给 §A1.5 的备份+横幅路径）
6) mapper 产出的 List<MigrationIssue> 写入 settings 键 `migration_v13_report`（设置页可读，条数与原因）
```
**`LegacyTaskRow` 必须是独立 DTO，不能是 `TaskEntity`**（v14 删实体字段后 `TaskEntity(taskType=…)` 就编不过；评审 B-MF2）。DTO 与 `MigrationIssue` 一律放 `data.db.entity` 包内 —— `app/proguard-rules.pro:2` 只 keep 了该包，GSON DTO 放别处会在 release 静默丢字段。

映射规则照 `00-总体方案-v2.md` §2.4 表，特别注意三条 v1 漏掉的：
- 老 `dueDate` 里的 `HH:mm` → `remindTime`（否则迁移后每日提醒集体消失）；
- `isCompleted=1` 且无 `dailyCompletionDate`（weekly/once 的完成态）→ 用 `completedAt` 日期建 occurrence（否则完成历史无处安放）；
- occurrence 只产一条：有 `dailyCompletionDate` 时**不再**叠加 `completedAt` 分支（v1 两条规则重叠会写出双份）。

## A1.5 备份与失败防线（本次最高优先，用户数据只有一份）

1. `AppDatabase.getInstance` 前先 `DatabaseBootstrap.ensureDatabaseReady(context)`：
   只读打开 → `PRAGMA user_version` → 若为 12：把 `zhiwo_shiguangjian` + `-wal` + `-shm` 复制到
   `context.getExternalFilesDir("migration_backup")/pre_v13_<ts>/`（**不能放 filesDir**：release 非 debuggable 时 adb 取不出来，备份等于空气）。
2. 迁移内写 `tasks` 全表 JSON 到同一目录 → **回读并断言行数 == 老表 `COUNT(*)`**，失败即抛（不静默）。
3. 迁移内最后做 §A1.3 步骤 5 的行数/条数自检。
4. `ZhiwoApplication.onCreate` 改为**同步**调用一次 `ensureDatabaseReady()`（替换现在 :55-70 的异步预热+catch 里 rebuild 的写法），避免"某个 ViewModel 先抛 → 进程被杀 → 崩溃循环且永不生成备份"。
5. **去掉 debug 的 `fallbackToDestructiveMigration()`**（AppDatabase.kt:182）：现在 debug 包遇缺迁移会静默清库、不抛异常 → `rebuild()` 与新备份逻辑**都不执行**，"备份"形同虚设（评审 B-MF8 已核实这条推论链）。迁移链 v3→v13 完整，不需要兜底。
6. 失败标记：捕获迁移异常 → settings 写 `MIGRATION_FAILED=<ts>` + 保留备份路径 → 设置页顶部横幅「上次迁移失败，数据已备份在 …，点这里重试」。**这条必须实现**，否则用户只会看到闪退。
7. 设置页「恢复到升级前」：关闭 DB → 还原三件套 → 重启进程。只覆盖"迁移前一刻"，**不承诺通用回滚**，UI 文案照实写。

## A1.6 Room 校验风险与离线证伪（评审 B-MF7）

- 风险：Room 2.6.1 在打开时按结构化信息（`PRAGMA table_info` / `foreign_key_list` / `index_list`）校验实体与库是否一致。我们让"实体加 15 个字段"与"表加 15 个列"逐字对齐，并把新增 FK 写成列级 `REFERENCES`，就是为了让它对齐；但**本机无模拟器 → 无法离线证明 Room 会接受**。
- 因此加两道离线证据：
  1. `exportSchema = true` + `ksp { arg("room.schemaLocation", "$projectDir/schemas") }`，把 `12.json`、`13.json` 提交进 git（Room 自己算出的"它期望的表结构"）。
  2. 新增 JVM 用例 `SchemaVsMigrationConsistencyTest`：解析 `schemas/.../13.json` 的 `entities[]`，与我们手写 `MIGRATION_12_13` 里的 DDL 逐字段对账 —— 列名、类型、NOT NULL、DEFAULT、索引集合、FK 的 `onDelete/onUpdate`。任何一项不一致就红。这是无模拟器环境下最接近"真验"的手段（纯 JSON 解析，不引入 sqlite-jdbc）。
- 残余风险如实写进实测清单：真机首次启动 v13 是这条链路的唯一终验。

## A1.8 测试清单（可证伪，方法名挂编号）

映射 `MF-M01..M14`：4 种 taskType happy path；weekly 三种日期格式（含周日 ISO=7、非法回退 everyday）；once 空 dueDate；未知/空/带空格 taskType→adhoc+issue；`isCompleted+dailyCompletionDate` 只产 1 条 occurrence；无 dailyCompletionDate 用 completedAt；completedAt 5 种脏值（null/''/`2026-09-21`/`2026-09-21 12:00:00`/ISO Z/垃圾）各断言；`isPermanentlyCompleted` 同时产 occurrence 与 archived；孤儿 parentGoalId→goalId=null+issue 且**不建 goal**；5 任务共享同一 parentGoalId→只建 1 行 goal；taskType='goal' 与另一任务 parentGoalId 同记录→同一 goal 不重复建行；100 行混合→行数不变量（`MappedTask.size == rows.size`，无静默丢行）；幂等（同输入两次结果相等）；`remindTime` 从 `dueDate` 的 `HH:mm` 提取（含 `24:00`、缺分、非法）。
备份编解码 `MF-B01..B03`：JSON 往返相等（中文/emoji/引号/换行/null 字段）；行数自检失败必须抛；备份目录名含时间戳且重复运行不覆盖。
`SchemaVsMigrationConsistencyTest`：v13 全部 12 张表逐列断言（一条用例内遍历，失败信息指明哪张表哪一列）。
`MigrationSelfCheckTest`：给出行数不等/occurrence 数不符两种输入，断言抛出的异常消息含具体数字。
