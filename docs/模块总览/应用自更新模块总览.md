# 应用自更新模块总览

## 模块职责（一句话）

让 App 自己发现新版本、下载并唤起系统安装器完成升级：云端发新版 = 推一次代码，手机上点一下「检查更新」就能装到最新。

## 运作流程（数据真实流动顺序）

1. **发版源头：GitHub Actions 自动构建**。每次推代码到 `master`，GitHub 服务器上的 `.github/workflows/build-release.yml` 自动跑：全量克隆代码 → 用 JDK 17（Temurin）+ Gradle 8.2 执行 `assembleRelease` 打出签名 release 包 → 把包以固定文件名 `zhiwo-shiguangjian.apk` 传到仓库的 **latest Release**（tag 永远叫 latest，永远只覆盖这一个发布，不堆一堆版本号）。Release 描述第一行写元数据 HTML 注释 `<!-- appupdate versionCode=21 versionName=1.1.21 -->`（GitHub 页面不显示这行，是给 App 解析用的），下面跟最近 6 条提交标题作为更新说明。
2. **版本号来源：git 提交数**。`app/build.gradle.kts` 在构建期跑 `git rev-list --count HEAD`，把提交数作为 `versionCode`、`1.1.<提交数>` 作为 `versionName`。本机构建和 CI 构建对同一个提交算出同一个号，每推一次自动 +1；CI 克隆必须全量历史（workflow 里 `fetch-depth: 0`）。git 不可用时回退 1（宁可偏小，偏小只会「误报有更新」，不会「漏报」）。注意：数据库升不升级由 `AppDatabase.VERSION` 决定，跟这个号无关。
3. **检查：App 查 GitHub API**。`UpdateChecker.check()` 用 `HttpURLConnection` GET `https://api.github.com/repos/Lwb1397111398/zhiwo-shiguangjian/releases/latest`，必须带 `User-Agent` 头（GitHub 强制，缺了 403）。仓库是公开的，匿名就能查（匿名限流每小时 60 次，配合 24 小时节流足够）。拿到 JSON 后 `parseReleaseJson()` 解析：第一行正则抓 versionCode/versionName → 资产列表里找 `.apk` 结尾的条目拿下载地址和文件大小 → 把描述去掉元数据行剩下的正文当「更新说明」。远端 versionCode 比本机（`PackageManager` 查已装包）大才算有更新。
4. **两个检查时机**：① 启动静默检查——`MainActivity` 的 `DbState.Ready` 分支里 `UpdateManager.maybeCheckOnStart()`，24 小时只查一次（时间戳写在 `filesDir/update_last_check.txt`），失败或已是最新就当无事发生；② 手动检查——设置页「应用更新」分区的「检查更新」按钮，结果（含失败原因）直接显示在设置页。
5. **下载：不留半截包**。`UpdateDownloader.download()` 流式下载（64KB 缓冲），先写 `cacheDir/updates/update-<versionCode>.apk.part`，下完校验字节数与远端一致才改名转正；同版本完整包已存在就直接复用不重下。进度回调（已下载字节/总字节）实时推进 UI 进度条。
6. **安装：系统安装器**。下载完 `UpdateManager` 先看有没有「安装未知应用」授权（`canRequestPackageInstalls()`）：有就直接唤起系统安装器；没有就跳系统开关页 + Toast 提示「开完回来再点一次」。APK 通过现有 FileProvider（authority `${applicationId}.fileprovider`，`file_paths.xml` 里新开了 `cache/updates/` 子目录）给系统临时读权限。覆盖安装不打扰用户数据（数据库迁移归数据层管）。

## 入口文件清单

- `.github/workflows/build-release.yml` — 云端自动构建 + 发 latest Release
- `app/build.gradle.kts` — 版本号=提交数、统一签名配置
- `android/keystore/app.keystore` — 签名钥匙（PKCS12，口令 android / 别名 androiddebugkey）
- `data/update/UpdateChecker.kt` — 查 API + 解析（纯函数可单测）
- `data/update/UpdateDownloader.kt` — 流式下载
- `data/update/UpdateInstaller.kt` — 权限判断 + 唤起系统安装器
- `data/update/UpdateManager.kt` — 状态机总管（静默检查节流、下载安装编排）
- `ui/update/UpdateUi.kt` — `UpdateSection`（设置页分区）+ `UpdateHost`（全局弹窗）
- `ui/screens/SettingsScreen.kt` — 插入「应用更新」分区（存储状态之后）
- `MainActivity.kt` — Ready 分支挂静默检查 + `UpdateHost()`
- `AndroidManifest.xml` — `REQUEST_INSTALL_PACKAGES` 权限
- `res/xml/file_paths.xml` — FileProvider 开 `updates/` 子目录
- `app/src/test/.../UpdateCheckerTest.kt` — 解析/比较单测（不联网）

## 对外接口 / 被谁调用

- 被调用：`MainActivity`（静默检查 + 弹窗宿主）、`SettingsScreen`（分区 UI）。
- 对外只暴露 `UpdateManager`（状态 `StateFlow` + 动作方法）和两个 Composable（`UpdateSection`/`UpdateHost`）。
- 依赖的云端契约：`build-release.yml` 发的 latest Release 格式（元数据注释第一行 + 单个 .apk 资产）。两边改一边都要同步另一边。

## 依赖的上游模块

- 无数据层依赖（不碰 Room，不读设置表）——更新模块整体自包含，断网也不影响其他功能。
- UI 复用 `SettingsScreen.kt` 里的 `SectionTitle`/`StorageRow`。

## 关键数据结构

- `UpdateInfo(versionCode, versionName, downloadUrl, sizeBytes, notes)` — 远端新版本信息。
- `UpdateState`（sealed interface）：`Idle / Checking / UpToDate / Available / Downloading / ReadyToInstall / Failed` — 单一 `StateFlow`，设置页与弹窗同源消费。
- 签名：debug 与 release 两个 buildType 都锁 `android/keystore/app.keystore`——任何环境构建的包签名指纹一致，才能互相覆盖安装。

## 已知坑与约束

- **仓库必须公开**（大号 `Lwb1397111398/zhiwo-shiguangjian`）：匿名查/下载才通；私有仓库 API 返 404，App 会一直报「云端还没有任何发布」。
- **签名钥匙随公开仓库公开**：口令本来就是公开的 debug 惯例口令，签名一致不授予任何安装/数据权限，个人项目风险可控；介意的话以后再换钥匙（换了之后手机要先卸载重装一次，数据会丢，需提前导出）。
- **CI 三坑已修**：`gradlew` 执行位（`git update-index --chmod=+x` 修成 100755）；CI 上跳过美团内网镜像（`settings.gradle.kts` 按 `CI=true` 环境变量分流）；wrapper 华为云分发源在 workflow 里 sed 换成官方源（本机不改，避免重下 100MB）。
- **本机构建必须走 `tools/verify.sh`**（中文路径问题）：镜像目录含 `.git`（robocopy /MIR 会带上），所以镜像里也能算提交数，版本号与真目录一致。
- **minSdk 26 正好满足**：`canRequestPackageInstalls()`/「安装未知应用」都是 API 26+。
- R8：`proguard-rules.pro` 里 `-keep class com.zhiwo.shiguangjian.data.**` 已覆盖 `data.update` 包，无需额外规则。
