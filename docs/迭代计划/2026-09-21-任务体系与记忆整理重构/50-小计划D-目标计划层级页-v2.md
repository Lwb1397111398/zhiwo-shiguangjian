## D.1 层级与不变量

```
Goal（长期）─┬─ Plan（一段时间）─┬─ Task（daily / adhoc / blank）─ TaskOccurrence（每天一条）
             └─ Task（直挂目标的任务）┘
```
1. `tasks.goalId`、`tasks.planId`、`tasks.recordId` **一律 `ON DELETE SET NULL`**（v13 用列级 REFERENCES，v14 重建表时定型 recordId 的语义）。删除永远由代码显式决定，不靠 DB 级联偷删数据 —— 这正是本轮要修的老毛病。
2. `planId != null` 时 `goalId` 必须等于 `plan.goalId`；不一致时编辑器以 plan 为准纠正（C2.2）。**进度只按 plan 计**，goal 再合并其下 plan（B 的 `MF-D03` 已锁死"不双算"）。
3. 固定深度 3，无自引用 → 天然无环（写进注释，防后人加"子目标"）。
4. `task.planId`/`goalId` 指向的对象 `status != active` → 任务不进日计划（规则在 B，D 只负责传 `parentStatusById` 真值）。

## D.3 操作语义（v2 补完，逐条有测试或走查）

| 操作 | 行为 | 连带与提示 |
|---|---|---|
| 目标达成 | `goal.status='achieved'`；其下 active 计划 → `done`；**daily/blank 任务 → `status='archived'`**；adhoc 未完成任务**不动**，弹提示「仍有 N 个临时任务未完成，是否一并归档」 | 触发记忆对账 `reconcileAndApply("目标「X」已完成，这是用户确认的事实")`（迁移 RecordListViewModel.kt:259-272，能力不得丢） |
| 放弃目标 | `goal.status='abandoned'`；计划 → `dropped`；任务同上 | 对账文案「已放弃（未达成）」 |
| 删除目标 | 二次确认，二选一：「同时删除 N 个计划、M 个任务及其 K 条打卡记录」/「保留计划（变为独立计划）」 | 前者代码显式级联删（FK 是 SET NULL，不显式删就删不掉）；后者 `plan.goalId=null` |
| 删除计划 | 确认「其下 M 个任务变为自由任务，打卡史保留」 | 任务 `planId=null`，**不删任务** |
| 暂停/恢复计划 | `plans.status='paused'` | 计划内任务当天起从日计划消失（引擎按 §D.1-4） |
| 归档/删除任务 | `status='archived'` / 物理删（连带 occurrence，数字真实显示） | — |

`GoalRepository.deleteGoal(mode=CASCADE|DETACH)` 与 `abandon/achieve` 都写成**单事务**，且事务内不碰闹钟/日历（闹钟取消放事务后的 `ScheduleSyncService`，F 实现；避免事务里做 IPC）。

## D.4 AI 拆解（目标 → 计划 → 任务）

- 入口：目标详情页「AI 拆解建议」。`AiRepository.decomposeGoal(goal, activeMemories): GoalDecomposition` + `AiPrompts` 新模板，输出 `{plans:[{title,startDate,endDate,tasks:[{content,kind,repeatRule,weekdaysCsv,durationMinutes}]}]}`。
- **不采信模型日期**：`startDate/endDate` 一律由本地按 `goal.targetDate` 均匀切分覆盖（模型只出标题与任务）；`kind` 非法 → 按 `repeatRule` 是否存在回退 `daily/everyday`，否则 `adhoc`（评审 SHOULD：不要一律回退 adhoc）；`weekdaysCsv` 脏值按 B 的清洗规则；任务数上限 30、计划数上限 8，超出截断并提示。
- 交互：草稿 BottomSheet（逐条删/改标题/调日期）→「确认创建」→ 单事务写入。
- **不进 `organize_ops`**（那张表语义是"整理既有数据"，这里是新建），但保留两阶段特征（预览→确认→一个事务）。
- AI 未配置：按钮置灰 + 说明；调用失败：保留草稿不崩；沿用 3 秒限速与 90 秒超时。
