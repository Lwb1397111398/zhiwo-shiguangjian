上游：总体方案 §8　依赖：E 的建表/加列部分并入 A 的 `MIGRATION_12_13`（避免 v14 二次迁移）；逻辑部分独立于 B/C/D
交付形态：里程碑 M2（可与 M1 并行开发，但必须同一版本发出，否则用户仍会看到残存）

## E.0 用户看到的现象与真实原因

现象：「一键整理之后不知为什么老有残存的记忆」。
经实地核查，"残存"不是一个 bug，而是 **7 个缺陷叠加**，每一条都能独立造成"我明明整理了，它还在"：

| # | 根因 | 证据 | 用户看到 |
|---|---|---|---|
| R1 | 整理执行链**没有任何一步物理删除记忆**，EVOLVE 只把 status 改成 `superseded` | OrganizeOpExecutor.kt:126-150 | 旧记忆只是被"划线"，还在页面上 |
| R2 | `superseded` 记忆仍渲染在「已更正的记忆（N）」区，且该区只有"恢复"没有"删除" | MemoryViewModel.kt:39-41 → MemoryScreen.kt:345-384 | 越整理，"已更正"区越长，感觉永远清不干净 |
| R3 | 判重是**整句完全相等**，近义/改写的旧记忆不会被取代 | OpValidator.kt:70-73（对比 ReviewViewModel.kt:383-403 才有归一化） | 同一件事 3 条说法不同的记忆同时 active |
| R4 | 上一批遗留的 PENDING/FAILED/STALE 提案，界面只认"最新批次" | OrganizeViewModel.kt:142-151、OrganizeOpDao.kt:31-32 | 上次没跑完的整理**永远不再出现也永不执行**，对应记忆原地不动 |
| R5 | `dismiss` 只把自己置 DISMISSED，不清下游 `dependsOn` | OrganizeViewModel.kt:458-463、OpValidator.kt:44-50 | 忽略一条建议 → 同批所有删除永久 BLOCKED（静默） |
| R6 | 每条删除提案的 payload 里塞的是**当前所选全部 id** | OrganizeViewModel.kt:585-615 | 勾 1 条删全部（过删），或不勾时一条都不删 |
| R7 | 记忆合并/拆分有**两套互不相通**的实现：记忆页那套硬删、无事务、无幂等校验，中途异常只提示"已完成 N 条" | MemoryViewModel.kt:246-392 vs OpPayloads.kt:9-16 | 合并到一半失败 → 留下半截重复；与整理页语义相反（一边 supersede 一边物理删） |
| 附 | `createdAt` 被写成来源日期，导致整理出的新记忆排在列表最底且**最先被上限淘汰** | OrganizeOpExecutor.kt:112-124、MemoryDao.kt:34-37 | "刚整理的记忆转头就没了" |

## E.1 修复方案（逐条对应）

**R1+R2 · 状态与可见性收口**
- 记忆页默认列表 = `status == 'active'`（不变），但**彻底去掉**"已更正的记忆"折叠区；改为记忆页顶部一行「已更正 N 条 ›」入口 → 二级页 `superseded_memories`，那里每条提供：**恢复**、**彻底删除**，顶部提供「清空全部已更正」。
- 自动清理策略：`superseded` 保留最近 30 条（可配），更旧的在应用启动的维护任务里物理删除，并记日志条数。理由：留 30 条足够反悔，不留则越积越多、上限统计也被污染。
- `getMemoryCount` 语义改为**只数 active**（MemoryDao.kt:30 现在把 superseded 计入），淘汰只能淘汰 `superseded`（最旧优先）→ 淘汰 active 前必须先证明 superseded 已清空。

**R3 · 判重换成归一化 + 近义判定（纯函数 + 单测）**
- 新增 `data/memory/MemorySimilarity.kt`：
  - `normalize(s)`：去首尾/重复空白、全角转半角、统一标点（，。！？→删除或半角）、去尾部语气词、小写化；
  - `level(a, b)`：`EXACT`（归一后全等）/ `CONTAINS`（一条完全包含另一条且长度差 ≤ 阈值）/ `SIMILAR`（字符 bigram Jaccard ≥ 0.72）/ `DIFFERENT`；
- 应用点：①`OpValidator` 的"已存在同内容"判断改用 `EXACT`+`CONTAINS`；②整理 apply 完成后，对 active 集合跑一次两两 `SIMILAR` 扫描，产出「疑似重复」提示（**不自动合并**，避免误删用户语义），点击进合并候选。
- 阈值 0.72 先定常量，测试里用真实中文样例校（含"我喜欢跑步"/"我喜爱跑步"判 SIMILAR；"我明天要考试"/"我要考试"判 CONTAINS 或 SIMILAR 但不判 EXACT）。

**R4 · 批次可见性**
- 整理页新增常驻顶部区「未完成的整理（N）」，数据源 `getOpsByStatusNotTerminal()`（跨批次），每条显示：类型、来源批次时间、状态（PENDING/FAILED/STALE/BLOCKED）、动作：**继续执行 / 重试 / 丢弃**。
- `applyBatch` 改为按 op id 集合执行（可跨批次勾选），不再隐含"只跑最新批"。

**R5 · dismiss 级联**
- `dismissOp(id)` → 递归把所有 `dependsOn` 含它的 op 一并置 DISMISSED（复用现有"取消勾选级联"逻辑 :522-557，抽成 `DependencyCascade.cancel(opId)` 纯函数），并在 UI 提示「同时取消 N 条依赖它的清理」。
- 提供「撤销忽略」：把 DISMISSED 及其下游恢复为 PENDING。

**R6 · 删除范围**
- `buildDeletePayload` 改为**每条提案只携带自己的 sourceIds**；「全部清理」由多条提案组成。
- 单测：勾 1 条只删 1 条；勾 3 条生成 3 条提案共删 3 条不同集合；`finalCleanable` 为空 → 0 条 DELETE 提案（现在就是这个行为，锁死）。

**R7 · 合并/拆分统一到 organize_ops**
- 新增 op 类型：`MERGE_MEMORY`（payload: `memoryIds[]`, `mergedContent`）、`SPLIT_MEMORY`（payload: `memoryId`, `parts[]`）、`DELETE_MEMORY`（payload: `memoryId`）。
- 执行器 `OrganizeOpExecutor` 增分支：MERGE = 事务内「插入合并后新行（status=active, createdAt=now）+ 把旧行置 superseded 且 supersededBy 指向新行」；SPLIT = 「插入 N 条新行 + 原行置 superseded 指向第一条」；DELETE = 物理删除（唯一允许物理删的路径，需二次确认）。
- 记忆页原来的 `applyMerge/applyEvolve/applySplit/applyAll` 改为**生成提案**（走同一张表、同一审核 UI），删除硬删实现。**语义统一为：整理只 supersede，物理删只有用户点"彻底删除/DELETE_MEMORY"时才发生。**
- STALE 校验沿用 `OpValidator` 的版本快照（memoryIds 内容 hash），避免"提案生成后用户又改了记忆"仍按旧内容合并。

**附 · createdAt 与来源日期解耦**
- `memories` 新增列 `occurredAt TEXT`（默认回填旧 `createdAt`），整理/对账写入时 `createdAt = now`、`occurredAt = 来源日期`；列表排序仍按 `createdAt DESC`，展示"来自 2026-08-23 的记录"用 `occurredAt`。
- ⚠ 该加列放进 A 的 `MIGRATION_12_13`（同版本一次迁移），E 不再单独提版本号 —— 这是 E 与 A 的唯一耦合点，必须写进 A 的 DDL。

## E.3 测试清单（可证伪）

`MemorySimilarityTest` ≥14 例：空/全空格、全角标点、大小写、`CONTAINS` 长度阈值边界、bigram 相似度 0.71 vs 0.73、中英混排、纯英文小写归一、"我喜欢跑步"vs"我喜爱跑步"=SIMILAR、"我在准备法考"vs"我今年通过法考"=DIFFERENT（防过度合并）、自反性（同句必 EXACT）。
`DependencyCascadeTest` ≥6 例：单层/三层链式依赖、环检测（防死循环）、级联后状态集合正确、撤销恢复、无依赖时只改自己、多父依赖（一条 op 依赖两条 SAVE）只在**全部**父被取消时才级联取消。
`OpValidatorTest` 扩充：`EXACT/CONTAINS` 判重不再放行、SPLIT/MERGE payload 校验（memoryIds 为空/只有 1 条时 MERGE 非法）、STALE 判定含内容 hash 变化。
`MemoryDaoCountTest` 若需 Robolectric 则跳过 → 改判为「计数 SQL 字符串断言 + 实测清单」，**不假装测过**。

## E.6 风险

| 风险 | 对策 |
|---|---|
| 判重过激 → 把用户不同含义的记忆合并掉 | 自动只做 `EXACT/CONTAINS`；`SIMILAR` 只提示不自动合；任何合并且物理删的都要二次确认 |
| 一次性改 7 条，回归面大 | 每条根因一个 commit + 对应测试；按 R3→R5→R6→R4→R1/R2→R7 顺序（先纯逻辑后 UI） |
| 已有 organize_ops 老数据（上一版遗留）在新规则下的展示 | 迁移时不改写历史 op，只按新查询展示；`STALE` 老 op 由用户手动丢弃 |
