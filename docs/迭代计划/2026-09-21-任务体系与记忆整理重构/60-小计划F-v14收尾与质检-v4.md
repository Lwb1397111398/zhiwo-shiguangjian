## 1. 红线（永久生效）

- **R1（唯一例外）**：本次 v13→v14 升级真出事时，现有手机数据允许丢一次。
- **R2**：v14 起所有迁移必须增量、保数据；禁止 `fallbackToDestructiveMigration`（含 debug 变体）。
- **R3**：迁移自带指纹断言（行数 + `SUM(id)`/`COUNT` 分桶 + 三态计数 + 抽样列校验），不一致就 `throw` 回滚，**不允许留半迁移状态**。
- **R4（v3→v4 新增，回应"MIGRATION 失败仍被 rebuild 静默清库"）**：**迁移异常一律不再自动清库**。`ZhiwoApplication` 捕获后写 `db_state.migrate_failed`（版本、异常摘要、时间），主界面渲染**升级失败页**：「你的数据还在（数据库停在 vX，没能升到 vY）」+ 三个按钮：`重试升级` / `导出诊断信息` / `清空重建`（后者需二次确认，确认后才走 `AppDatabase.rebuild`）。正常路径**永不显示**此页。
- **R5**：`AlarmReceiver` 触发时必须重新过引擎判定；不该响的日子静默吞掉并续排下一次。

## 2. 交付批次（每批独立可编译、独立跑 verify.sh）

### F-a 闹钟地基（前置于 #1，不然"接了引擎也是响错的"）
- `taskIdToAlarmId(t) = t*16 + 0`、`+1` 留给"当日"、`+2` 留给"续排"，slot 上限 16（远超实际 3 个用途，且注释写明不得再加 slot 而复用）。`notificationId` 另用 `20_000_000 + t`，与 requestCode 解耦，避免通知互相顶替。
- **老 requestCode 清理**：升级后首次启动跑一次性 sweep，对每个任务 cancel 旧公式的 `t+10000` / `t+10001` 两码（否则旧闹钟继续按老逻辑响，且新公式无法取消它）。
- `AlarmReceiver`：收到 `TASK_REMINDER` → 反解 taskId → `goAsync()` 内查 `isScheduledOn(今天) && occurrence 未 done` → 不满足则不弹通知；无论如何注册"下一次"单发闹钟（R5）。
- 每日重复闹钟语义：改为**单发 + 触发后续排**（`setExactAndAllowWhileIdle`），因为 `setInexactRepeating(INTERVAL_DAY)` 表达不了 `workday_only`/`weekdaysCsv`/`intervalDays`，会在休息日照响。
- 用例（JVM）：MF-a1 两任务 requestCode 不重号；MF-a2 cancel A 不影响 B；MF-a3 sweep 能枚举旧码；MF-a4 触发时非排期日→不弹且续排到下一排期日。

### F-b 开机恢复接引擎（#1 本体，依赖 F-a、F-c 的 resolver）
- `BootReceiver` 取数改为：`status=="active"` && `remindTime` 非空 → `nextScheduledDate(task, today, resolver = 引擎 dayTypeOf(带 HolidayCalendar ∪ 设备日历 ∪ day_overrides))` → 命中日未 done 才注册。
- **必须显式传 resolver**（默认 `{ null }` 会让 `workday_only` 永不排期 = 静默失响）。
- adhoc 不再走 `nextScheduledDate`（它对此语义不足）：改走"今天是否 `scheduled==今天 && !done`"同日判定；`nextScheduledDate` 内部也顺手补 adhoc 分支（`scheduledDate` 未到不返回今天），并加用例钉住。
- 预算保护：任务数上限 500、整批耗时打 Log；`today` 与 `triggerAt` 取**同一次时间快照**（开机早期时钟可能未校正）。
- 用例：MF-b1 暂停/归档不注册；MF-b2 `workday_only` 周六重启→下周一；MF-b3 留白任务（无 dueDate 老列）仍注册；MF-b4 当天已完成不注册；MF-b5 无 `remindTime` 不注册；MF-b6 adhoc 定在未来某天→今天不响。

### F-c `dueDate` 语义搬迁（删列的前置，需老板拍板 Q4）
- 新语义：`endDate` = 通用"最后一天/期限"。adhoc 的期限从 `dueDate` 搬进 `endDate`；`scheduledDate` 仍是"哪一天出现"。
- 改动：迁移里 `UPDATE tasks SET endDate=COALESCE(NULLIF(endDate,''),dueDate) WHERE kind='adhoc' AND endDate=''`；编辑器 adhoc 的"最后期限"字段改写 `endDate`；`TaskScheduleEngine.entriesFor`/`TaskSummaryBuilder`/`RecordListViewModel` 的 adhoc 期限判据改读 `endDate`。
- 用例：MF-c1 adhoc 期限当天算 scheduled、次日记为过期；MF-c2 无期限 adhoc 只在 `scheduledDate` 当天出现；MF-c3 迁移后老数据期限不丢（v13 有 dueDate 的行 → v14 endDate 相同）。

### F-d 升级失败可见（#2，独立于 v14，可先做）

- 用例：MF-d1 有 `migrate_failed` 标记时状态为真；MF-d2 无标记不显示；MF-d3 点"知道了/重试"清标记；MF-d4 **正常启动路径不写标记**（防误报）。

### F-f v14 迁移与实体减列（最后做，前六批都绿之后）

- 迁移 `MIGRATION_13_14` 顺序（照 `90-v4整合修订` §四 的实测模式）：
  1. `CREATE TABLE tasks_new`（20 列，`recordId` FK 改 SET NULL）；

  3. `INSERT INTO tasks_new SELECT …`（含 F-c 的 adhoc `endDate` 回填）→ `DROP TABLE tasks` → `ALTER TABLE tasks_new RENAME TO tasks`；
  4. **重建 `task_occurrences`** 并从快照回填 → 重建其两个索引；

### F-g 节假日设备日历源（#4，如实标注不承诺）
- 新增 `DeviceHolidayCalendarSource`：查 `Calendars`，**只接受白名单**：`CALENDAR_DISPLAY_NAME` 命中 `节假日|假期|中国节日|Holiday` **且** `ACCOUNT_TYPE` 非用户邮箱类（`com.google|com.huawei|com.xiaomi|android` 等本地/厂商类型）；命中日历的全天事件日期=休息日，标题含 `班|上班|调休|补班`=工作日。**不做**"任意全天事件当休息日"（会把 App 自己写的 `special_dates`/生日事件当成假期 → 排期被悄悄改）。
