## 0. 本轮锁定的事实（全部我亲自 grep/读 schema 核过，不再引"某代理说"）

- **S1 tasks 表 27 列**，v14 删 7 列（`taskType, dueDate, isCompleted, completedAt, dailyCompletionDate, isPermanentlyCompleted, parentGoalId`）→ 20 列。`recordId`/`calendarEventId` **保留**（前者是任务↔来源记录的活关联，后者被 7 处取消链路在读）。
- **S2 tasks 索引 4 个**：`index_tasks_recordId/parentGoalId/goalId/planId`。删 `parentGoalId` 列 → 它的索引必须一起消失，v14 实体只声明 **3 个**。
- **S3 tasks 外键 3 个**：`recordId→records CASCADE`（v14 改 `SET NULL`）、`goalId→goals SET NULL`、`planId→plans SET NULL`。**`parentGoalId` 没有外键**（v3 说它有，错）。
- **S4 `task_occurrences.taskId → tasks(id) ON DELETE CASCADE`** → 重建 tasks 必然级联清空打卡历史。**必须快照**，且快照要用 `CREATE TABLE … AS SELECT`（CTAS 不带任何约束，才不受级联与 RENAME 改写 FK 目标的影响）。
- **S5 唯一被 `tasks` 当父表引用的就是 `task_occurrences`**（13.json 全表外键遍历）。除此之外没有第二张。
- **S6 引擎 `isScheduledOn` 对 `kind` 非 daily/blank 的一律 `else -> true`**，不看 `scheduledDate` → `nextScheduledDate` 对 adhoc 直接返回"今天"，未来某天的临时任务会天天响。接线时必须给 adhoc 单独分支。
- **S7 闹钟 requestCode 现在就会串号**：`taskIdToAlarmId(t)=t+10000`、`dailyNextDayAlarmId(t)=前者+1` → 任务 t 的"明日提醒" == 任务 t+1 的"当日提醒"；`cancelTaskAlarm` 又固定多取消 `alarmId+1` → **取消 A 会掐掉 B**；`notificationId = alarm_id` → 两个任务的通知互相顶替。这是既有 bug，不是 v14 引入的。
- **S8 固定闹钟 ID 常量 1001~1004**（`AlarmData.kt`）与任务闹钟同处一个 requestCode 空间 → 新公式必须避开这个小整数区。
- **S9 `AlarmReceiver` 收到广播只发通知，不做任何"今天该不该做"的校验**；`setInexactRepeating(INTERVAL_DAY)` 表达不了 `workday_only`/`weekdaysCsv`/`intervalDays`。
- **S10 adhoc 的"最后期限"唯一存在 `dueDate`**：编辑器 `endDate` 只在 `kind=="daily"` 分支写（`ScheduleScreen.kt:458-460`），adhoc 的期限字段写 `dueDate`（`:400,459`）；引擎 `TaskScheduleEngine.kt:193`、摘要 `TaskSummaryBuilder.kt:73`、记录页 `RecordListViewModel.kt:125` 都读它。
- **S11 迁移失败的现行处理**：`ZhiwoApplication.kt:58-60` 在协程里异步预热 `writableDatabase`，catch 后直接 `AppDatabase.rebuild()` → 备份 → 删活库 → `INSTANCE=null` → 写 `db_state.rebuilt_at` → `killProcess+exitProcess(10)`。`database` 是 `by lazy` 属性，**一旦旧实例被使用过就无法重置**（注释里自己写了这点）→ 所以"确认后才清库"不能改成"就地重建继续跑"。
- **S12 依赖可用性（实测）**：`org.xerial:sqlite-jdbc:3.41.2.2` 已在本机 Gradle 缓存内，`repo1.maven.org` 直连 200；`app/build.gradle.kts` 的 `testImplementation` 目前只有 junit，**没有** `MigrationTestHelper`。
- **S13 设备 SQLite 版本**：minSdk 26/27/28 ≈ SQLite 3.19~3.24，**不支持 `ALTER TABLE DROP COLUMN`（要 3.35+）** → v14 只能走"重建表"，且迁移语句里不许出现新版本才有的语法；本机 JVM 测试用 3.41，**测试通过不代表低版本可用**，故 §5 有"低版本语法白名单"。
- **S14 `CalendarHelper.getPrimaryCalendarId` 只投影 `_ID, IS_PRIMARY`**，写事件写进主日历；`addEvent` 后固定插 15 分钟 `METHOD_ALERT`（与自研闹钟双响）。
- **S15 `HolidayCalendar` 只有 2026**；三页统一走 `dayTypeOrWeekend`（无数据年按周末猜 + 顶部提示）。闹钟侧若用 `dayTypeOf`（无数据年返回 null）会让 `workday_only` 任务**永不排期 = 静默失响**。
- **S16 `getTasksByParentGoalId` 是活的**（`RecordOrganizer.kt:167`），不是零调用 → 删列前必须先转成按 `goalId` 取数。

## 1. 红线（与 v4 同，R4 具体化）

R1 本轮升级真出事允许丢一次；R2 v14 起禁止任何静默清库、禁 `fallbackToDestructiveMigration`；R3 迁移自带指纹断言，不符 `throw` 回滚；R5 闹钟触发时必须重过引擎。
**R4（升级失败门，本轮定实现路径）**：
1. `AppDatabase` 迁移异常不再走 `rebuild()`，改为写 `db_state.migrate_failed`（含 fromVersion/toVersion/异常类名与 message 摘要/时间戳）后**不再预热**；
2. `MainActivity` 在**打开任何页面前**同步读 `db_state.migrate_failed`（纯 SharedPreferences，不碰数据库），据此选 `DbState.UpgradeFailed` 分支渲染 `DbUpgradeFailedScreen`，正常时 `DbState.Ok` 才构建 `NavHost`；
3. 该页只给三条出路：`重试升级`（清标记 → `Process.killProcess` 冷启，让迁移再跑一次）/ `复制诊断信息`（异常摘要）/ `清空重建`；
4. `清空重建` 必须**二次确认**（输入不是勾选，而是复述"我知道数据会被清空"），确认后写 `db_state.rebuild_confirmed` → 调 `AppDatabase.rebuild()` → 沿用现有 `killProcess + exitProcess(10)`。**不清 INSTANCE、不就地继续用**：`database` 是 `by lazy`、旧句柄指向已删文件，就地重建必然拿到坏连接（S11）。冷启动后 `rebuilt_at` 存在 → 设置页顶部横幅「上次升级没能搬完数据，已重建空库；备份在 `Android/data/…/files/migration_backup/<pre_rebuild_ts>`」+「知道了」清标记。

### F-c 语义搬迁（v5 细化，解决 N2 的"空窗期"）
- **读侧统一到一个函数**：`AdhocDeadline.of(task) = task.endDate.ifBlank { task.dueDate.take(10) }`（F-f 删列后 `dueDate` 那半自动退化为空）。所有 adhoc 期限判断改走它：`TaskScheduleEngine.kt:193`、`TaskSummaryBuilder.kt:73`、`RecordListViewModel.kt:125`、`CalendarGrid.kt:33`、`TaskItem.kt:74-76`、`ScheduleScreen.kt:400-401`。
- **写侧**：编辑器 adhoc 的"最后期限"改为写 `endDate`，同时（F-f 之前）仍镜像写 `dueDate`，保证回滚到 v13 代码也不坏。
- **迁移回填**（放在 F-f 的 `INSERT … SELECT` 里，不在生产 SQL 里做二次 UPDATE，少一个失败点）：`endDate = CASE WHEN kind='adhoc' AND endDate='' THEN substr(dueDate,1,10) ELSE endDate END`（`dueDate` 可能带 ` 09:00:00`，见 `RecordOrganizer.kt:125`）。
- 用例：MF-c1 只填 dueDate 的老行期限不丢；MF-c2 两者都有值时以 endDate 为准；MF-c3 无期限 adhoc 只在 scheduledDate 当天出现、次日记过期；MF-c4 镜像写仍成立（F-f 之前）。

### F-a 闹钟地基（v5 细化，解决 N8/N9）
- 新码表：`slotOf(t,slot) = 20000 + t*16 + slot`（slot 0=当日提醒、1=续排、2..15 保留，注释写明**不得复用 slot 表达别的语义**）；`notificationId = 1_000_000 + t` 与 requestCode 彻底解耦。基址 20000 避开固定闹钟 1001~1004（S8），`t*16` 在 Int 范围内可容纳约 1.3 亿任务，仍加 `require(t in 0..130_000_000)` 防溢出。
- **旧码一次性 sweep**：`db_state.alarm_id_v2` 标记，用 `commit()` 写入成功后才跑；跑的是"对每个未完成任务 cancel 旧码 `t+10000` 与 `t+10001` + `NotificationManager.cancel(同两个 id)`"，cancel 幂等所以中途崩溃可重跑；跑完写 `=2`。
- **提醒形态改单发+续排**（S9）：`setExactAndAllowWhileIdle` 注册"下一个排期日"，`AlarmReceiver` 触发时按 R5 重判（不该响就静默），随后注册下一次 → 策略日/间隔日不会错响。
- **失效率如实处理**：单发链路丢了（省电策略、-force-stop、时钟跳变）就没人补，故加三个补排点：① `MainActivity onStart` 增量校对；② `BootReceiver`（已有）；③ 新增 `ACTION_TIME_CHANGED / ACTION_DATE_CHANGED / ACTION_TIMEZONE_CHANGED / PACKAGE_REPLACED` 过滤器。**并在 `用户实测清单.md` 记为 USER 项**：锁屏/休眠/改系统时间后是否仍响，本机无法断言。
- 用例：MF-a1 任意两任务 requestCode 不重号（含 t 与 t+1 相邻）；MF-a2 cancel A 不影响 B；MF-a3 新码不与 1001~1004 重叠；MF-a4 sweep 幂等（跑两次结果同）；MF-a5 非排期日触发 → 不弹通知且续排到下一排期日；MF-a6 `intervalDays=3` 从 startDate 起算的排期序列正确。

### F-b 开机恢复接引擎（v5 细化，解决 N3）
- resolver **必须用 `dayTypeOrWeekend`**（与安排页/日历页同一把），并把 `HolidayCalendar` + 设备日历 + `day_overrides` **一次预载成集合**再喂闭包，不在循环里逐日查库。理由（S15）：用 `dayTypeOf` 会在无数据年返回 null → `workday_only` 永不排期 = 静默不响。

- 用例：MF-b1 暂停/归档不注册；MF-b2 `workday_only` 周六重启 → 下周一；MF-b3 留白任务无 `dueDate` 也注册；MF-b4 当天已 done 不注册；MF-b5 无 `remindTime` 不注册；MF-b6 adhoc 在未来日 → 今天不响；MF-b7 2027 年（无节假日数据）`workday_only` 仍按周末给出日期（不许返回 null）。

### F-f v14 迁移（照抄基准文档 §四 的已实测序列，解决 N1/N10）
```
0) 基线指纹：tasks 与 task_occurrences 各算 cnt / sum(id) / sum(length(content)) / 三态计数
1) CTAS 快照子表：CREATE TABLE task_occurrences_bak AS SELECT * FROM task_occurrences   -- 无约束，免疫级联
2) ALTER TABLE tasks RENAME TO tasks_old                                                -- 子表 FK 此刻指向 tasks_old
3) CREATE TABLE tasks (<20 列 v14 DDL，recordId 外键 ON DELETE SET NULL>)                -- 显式列清单，禁 SELECT *
   INSERT INTO tasks(显式列) SELECT 显式列, CASE…endDate 回填… FROM tasks_old
4) DROP TABLE tasks_old                                                                  -- 无行，级联无副作用
5) CREATE INDEX index_tasks_recordId / _goalId / _planId                                 -- 只 3 个（S2），且在 DROP 之后
6) DROP TABLE task_occurrences → 按实体逐字重建（2 个索引）→ INSERT … SELECT 显式列 FROM task_occurrences_bak → DROP 快照表
7) 断言：两表 cnt/sum(id)/sum(length(content))/三态计数与基线相等；PRAGMA foreign_key_check 为空；否则 throw
```
- **14.json 引导**：先临时 `version=14` + 空迁移 → `bash tools/verify.sh kspDebugKotlin --rerun-tasks` 生成 `14.json` → 把 DDL 逐字抄进迁移与实体 → 再补真正的迁移。实体一律**不写** `@ColumnInfo(defaultValue)`（v13 实测的比对规则）。
- **低版本语法白名单（S13）**：迁移只允许 `CREATE TABLE/AS SELECT`、`INSERT…SELECT`、`DROP TABLE`、`ALTER TABLE RENAME`、`CREATE INDEX`；**禁止** `ALTER TABLE DROP COLUMN`、`PRAGMA legacy_alter_table`（不作正确性依据）、`writable_schema`、`foreign_keys=OFF`（迁移事务内是 no-op）。
- **迁移语句抽 `internal fun migration13To14Statements(): List<String>`**，生产 `MIGRATION_13_14` 与 JVM 测试共用同一份，杜绝"测的不是跑的"。
- **JVM 迁移测试（S12 已核实可做）**：`testImplementation("org.xerial:sqlite-jdbc:3.41.2.2")`；夹具用 `13.json` 的 `createSql` 建库（要替换 `${TABLE_NAME}` 占位符、按外键依赖顺序建表、`PRAGMA foreign_keys=ON` 显式打开以模拟 Room）、灌 ≥3 条 occurrence + 混合 kind/带时间 dueDate 的 tasks → 跑语句 → 断言上面整串指纹。差异如实记账：本机 JVM 是 3.41，设备可能 3.19，故 §5 的白名单是硬约束，且真机升级仍列为 USER 项。
- 用例：MF-f1 13→14 指纹全等；MF-f2 occurrences 一行不丢（含三态计数）；MF-f3 索引集合与 `14.json` 一致（3 个，无 parentGoalId）；MF-f4 `recordId` 外键动作确为 SET NULL（删记录后任务行仍在、recordId 为 NULL）；MF-f5 adhoc 期限回填正确；MF-f6 `foreign_key_check` 为空；MF-f7 v12→v13→v14 链跑通（同一夹具串两段迁移）。

### F-g 节假日设备日历源（v5 细化，解决 N10 之外的误判与 API 现实）
- 判定用**正向白名单**（不是"排除邮箱类"）：`ACCOUNT_TYPE IN ('com.google.android.calendar','com.huawei.android.calendar','com.xiaomi.android.calendar','com.android.calendar')` **且**显示名命中 `节假日|假期|中国节日|Holiday` **且** `VISIBLE=1`；显示名 API 26 起 deprecated → 取 `COALESCE(CALENDAR_DISPLAY_NAME, OWNER_NAME)`。
- 事件侧：全天事件日期=休息日；标题含 `班|上班|调休|补班`=工作日。**App 自己写的事件落在主日历**（S14），主日历名字不含"节假日" → 不会被自己的白名单吃进去；仍加一条排除"由本 App 写入的事件"（描述里已带来源标记）双保险。
- 设置页如实显示"节假日来源：内置 2026 / 设备日历《名字》 / 未找到（按周末猜）"。找不到就**不假装**：`holidayWarning` 文案保留。
- 用例：MF-g1 `day_overrides` 压过一切；MF-g2 无匹配日历时输出与今天逐条相同（回归）；MF-g3 主日历里 App 写入的全天工作事件**不会**被当假期；MF-g4 无 READ_CALENDAR 权限时不崩不弹、直接降级。
