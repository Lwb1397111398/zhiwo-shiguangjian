## A1.0′ 迁移 DDL 的唯一正确姿势（本节以此为准，与下表冲突时以本节为准）

**不手写"猜 Room 想要什么"的 DDL。** Room 会为每张表在 schema JSON 里生成它自己期望的 `createSql` 原文、字段表、索引表（含名字与 unique 标记）、外键表（含 onDelete/onUpdate）。迁移里就执行这些原文，一个字都不自己编。

执行顺序（A1 开工时照做）：
1. `exportSchema = true` + `ksp { arg("room.schemaLocation", "$projectDir/schemas") }` —— **已完成**，且 `12.json` 已在任何 v13 改动之前生成（Room 只导出**当前** version 的 schema，v13 落地后就再也补不出 12.json 了）。
2. 加实体字段 + `@Database(version = 13)`，编译一次 → 得到 `schemas/…/13.json`。
3. `MIGRATION_12_13` 的新表部分 = 13.json 里那张表的 `createSql` 原文 + 由 `indices[]` 生成的 `CREATE INDEX`（名字照抄）；`tasks` 老表用 `ALTER TABLE ADD COLUMN`，列定义取 13.json 的 `fields[]`（`TEXT NOT NULL DEFAULT 'adhoc'` 这类字面量照抄；FK 列不带 DEFAULT，可直接写 `REFERENCES`）。
4. JVM 用例 `SchemaMigrationConsistencyTest`：把 13.json 的 createSql/fields/indices/foreignKeys 与 `MIGRATION_12_13` 的 DDL 做**归一化对账**（表名、列名+类型+notNull+defaultValue、索引名与列序、FK 的 onDelete/onUpdate）。不一致即红。
   → 这样"实体改了忘改迁移"从构造上就不可能发生，也不需要我赌 Room 的校验细节。

| C-1 | **`ALTER TABLE ADD COLUMN` 不能带 `REFERENCES`**（SQLite 语法的 ALTER TABLE 规则明确：ADD COLUMN 的约束列不含 foreign-key-clause）；且 Room 的 `TableInfo.create` 用 `includeForeignKeys=false` → 实体写了 FK，迁移没写，**13.json 里也不会有 FK，v2 的对账测试会"假绿"** | v13 **删掉两行 `REFERENCES`**，`tasks.goalId/planId` 只作为普通可空列 + 索引存在；**Kotlin 侧显式置 NULL**（`GoalRepository.deleteGoal` 与 `PlanRepository.deletePlan` 内 `UPDATE tasks SET goalId=NULL WHERE goalId=?`）；并在 `GoalEntity/PlanEntity/TaskEntity` 上**都不声明这三个字段的 ForeignKey**，让实体与 13.json 完全一致 |

## A1.2 回填（v13 迁移内，纯函数 + 参数绑定）

```
1) goals ← **所有** records WHERE category IN ('goal')（不只被 parentGoalId 引用的），
   按 id 升序建 goal 行，createdAt = 该记录的 createdAt；title 空则取 content，再空则「未命名目标」；
   同时产出 map<oldRecordId, newGoalId>
2) 读老 tasks 全表 → List<LegacyTaskRow> → LegacyTaskMapper.mapAll(rows, goalIdOf, today)
   → (updates: List<TaskUpdate>, occurrences: List<MappedOccurrence>, issues: List<MigrationIssue>)
3) 逐行 UPDATE tasks SET kind=?,repeatRule=?,... WHERE id=?（占位符绑定，禁字符串拼接）
4) INSERT INTO task_occurrences(...) 回填历史
5) 自检（失败一律走 P2 恢复模式，不得 rebuild）：
   COUNT(tasks) == tk0；
   COUNT(DISTINCT taskId FROM task_occurrences) == mapper 断言值；
   COUNT(task_occurrences) 在 (taskId,date) 分组下无重复；
   issues 条数 == 期望（不达标即抛，异常消息含具体数字）
6) issues 写 settings 键 `migration_v13_report`（设置页可读，含"未能识别 N 条 / 提醒回填 N 条 / 孤儿目标 N 条"）
```
映射规则沿用总体方案 §2.4（含 `dueDate` 的 `HH:mm` → `remindTime`、`isCompleted` 无 `dailyCompletionDate` 时用 `completedAt`、`isPermanentlyCompleted` → `status='archived'`、**goal 行从全部 goal 记录生成**）。v3 追加：

- **`goalId` 归属权威源**：`LegacyTaskMapper` 增入参 `recordCategoryById: Map<Long,String>`。
  - `parentGoalId != null` → 若 `recordCategoryById[parentGoalId] == "goal"` 则 `goalId = map[parentGoalId]`；否则视为脏值 → `goalId = null` + issue `GOAL_CATEGORY_MISMATCH`；
  - `parentGoalId == null && taskType == "goal" && recordCategoryById[recordId] == "goal"` → `goalId = map[recordId]`；
  - 其它 → `null`。禁止用"命中 map 即当目标是目标"这种弱判定（一条 `category='idea'` 的旧 parentGoalId 记录会被凭空造出一个目标，老板会看见它多出来的目标行）。
- **同一条 goal 记录只产出一行 goal**（多条任务共享同一 parentGoalId / 一个 `taskType='goal'` 任务的 recordId 恰好等于别的任务的 parentGoalId，都指向同一行）。
- 老 `completedAt` 写入时用的是 `nowDate()`（RecordListViewModel.kt:154），v13 之前该列**恒为纯日期无时间** → 用例 MF-M11 注明这一点，别拿不存在的格式当输入。

## A1.5 记录删除不再连带抹任务（总方案 MF-2）
`RecordRepository.deleteRecord(id)` → 拆：
- `deleteRecordDetachingTasks(id)`：`UPDATE tasks SET recordId=NULL WHERE recordId=id` + 删标签/关键信息 + 删记录。**默认全部调用点改这个**（`RecordListViewModel.deleteRecord`、`RecordOrganizer:47/83/102/153`）。
- `deleteRecordCascade(id)`：保留原语义（连任务一起删），只在用户显式选择「连同任务一起删除」时走，UI 必须显示真实条数。

- `RecordOrganizer.kt:43-46`（"已完成的任务"被丢进 `completedTasksToCancel` 然后被物理删）→ 改为迁移到新记录，不删。

## A1.6 备份、失败分级与恢复模式（本次最高优先）
1. `DatabaseBootstrap.ensureDatabaseReady(ctx)`（`ZhiwoApplication.onCreate` 同步调用，替换现有 :55-70 的异步预热 + catch 里 rebuild）：
