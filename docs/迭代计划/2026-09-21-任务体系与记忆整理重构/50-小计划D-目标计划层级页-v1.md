## D.0 用户诉求原文对应

> 「计划就是一段时间的具体计划，比如这一个月我要看什么书、要一直学习法考知识直到下个月过法考」
> 「目标就是设定的长期的目标，比如今年要如何如何。目标分成多个计划，计划再分解成任务」

现状：**目标不是实体**（是 `RecordEntity(category=="goal")`，RecordListViewModel.kt:130-132、200-256），计划这个概念**完全不存在**（无表、无 UI、无字段）。所以 D 是补齐"中间层"，不是美化。

## D.1 层级与不变量

```
Goal（长期，如"今年通过法考"）
 └─ Plan（一段时间，如"9 月：民法精讲 + 真题 2 套/周"，起止日期）
     └─ Task（具体动作，kind=daily/adhoc/blank）
         └─ TaskOccurrence（每天一条打卡，含未完成原因 / 留白回填）
```
不变量（都要有测试或校验）：
1. 任务可以只挂 goal（不挂 plan），也可以只挂 plan（goal 由 plan 反推），**两者都为空 = 自由任务**（今天照常在每日段出现）。
2. `task.goalId` 与 `task.planId` 同时非空时，必须满足 `plan.goalId == task.goalId`；不一致时编辑器**以 planId 为准并自动纠正 goalId**（避免两级归属打架），校验函数 `TaskEditValidation.alignHierarchy(task, plan)`。
3. 一个 occurrence 只属于一个 task（外键 CASCADE），删任务即删打卡史 —— 删除确认里必须显示真实条数。
4. 层级不允许成环：goal→plan→task 是固定深度 3，无自引用，天然无环（明确写出，避免有人加"子目标"）。

## D.4 操作语义（删除/达成/放弃）

| 操作 | 行为 | 连带 |
|---|---|---|
| 标记目标达成 | `goal.status='achieved'`，其下 active 计划→`done`，直属/计划内任务：daily → `status='archived'`（不再刷新）、adhoc 未完成 → 保持？ | **不自动改任务状态**。理由：目标达成了但某个临时任务（交材料）可能还要做。仅归档 daily/blank 类重复任务，adhoc 留给人处理，UI 明确提示"仍有 N 个临时任务未完成，是否一并归档" |
| 放弃目标 | `goal.status='abandoned'`，计划→`dropped`，同上提示 | 触发记忆对账 `reconcileAndApply("目标「X」已放弃（未达成）…")`（保留 RecordListViewModel.kt:259-272 的既有能力，改成按 goal 行） |
| 达成同样触发对账 | `reconcileAndApply("目标「X」已完成，这是用户确认的事实")` | 现行为迁移，不得丢 |
| 删除目标 | 二次确认，弹出选择：「同时删除 N 个计划及其任务」/「保留计划（变为独立计划）」 | 前者需显式级联删（FK 是 SET NULL，所以必须代码里真删），后者 `plan.goalId=null` |
| 删除计划 | 确认「其下 M 个任务将变为自由任务（打卡史保留）」 | 任务 `planId=null`，**不删任务** |
| 暂停/恢复计划 | `status` active↔dropped? 不，新增 `paused` 到 plans | 计划内任务从日计划消失（引擎按 plan.status 过滤）→ 这是 B 需补的一条规则，记为 B-补充：`task.planId` 非空且该 plan.status != active 时，任务不进日计划（goal 同理） |

⚠ D.4 最后一条会回头改 B 的引擎（`buildDayPlan` 需要拿到 plans/goals 状态）。为避免"改完 D 打破 B"，把 `buildDayPlan` 的入参在 B 就设计成含 `parentStatusById: Map<Long, String>`（缺省空 map 即不启用该过滤），B 先实现 + 测（用空 map 与含 paused 两组用例），D 只是开始传真值。

## D.5 AI 拆解（目标 → 计划 → 任务）

- 入口：目标详情页「AI 拆解建议」。
- 新增 `AiRepository.decomposeGoal(goal: GoalEntity, activeMemories: List<MemoryEntity>): GoalDecomposition`，新 prompt 模板在 `AiPrompts.kt`，输出 JSON：`{plans:[{title,startDate,endDate,tasks:[{content,kind,repeatRule,weekdays,durationMinutes}]}]}`。
- **事实底线约束**：沿用现有 prompt 的接地要求（AiPrompts 里"事实底线"模式），并要求模型不得编造用户没说过的具体日期——`startDate/endDate` 缺省时由本地按目标 `targetDate` 均匀切分填充，不采信模型日期（在解析层强制覆盖，写测试）。
- 交互：生成 → BottomSheet 草稿树（可逐条删/改标题/调日期）→ 「确认创建」→ 事务内写入 goals/plans/tasks。
- 不进 `organize_ops`（理由：那张表语义是"对既有数据做整理"，这里是"新建"；混用会让 E 的审核链路语义腐化）。但**必须保留两阶段特征**：先看草稿再落库，且落库是一个事务。
- AI 未配置/失败：按钮置灰 + 说明「需要先在设置里配置 AI」；失败时保留草稿不崩。
- 限速：沿用 AiRepository 现有 3 秒最小间隔与 90 秒超时。
